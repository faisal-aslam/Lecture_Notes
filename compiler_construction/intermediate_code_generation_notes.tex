\section{Introduction: Why Intermediate Code?}
%====================================================================

In the \emph{analysis--synthesis} model of a compiler, the \textbf{front end} analyses the source program and produces an \textbf{intermediate representation (IR)}; the \textbf{back end} synthesises the target program from that IR.

\subsection{Advantages of using an intermediate representation}
\begin{itemize}
\item \textbf{Retargeting.} A compiler for $m$ languages and $n$ machines needs only $m$ front ends plus $n$ back ends ($m+n$ pieces instead of $m \times n$ separate compilers) if they share one IR. For example, 3 languages and 4 machines need $3+4=7$ pieces instead of $12$ compilers.
\item \textbf{Machine-independent optimisation.} Optimisations (common sub-expression elimination, constant folding, loop-invariant code motion, ...) are applied once on the IR.
\item \textbf{Simplicity.} Complex source constructs are lowered to a few simple operations, making code generation easier.
\end{itemize}

\begin{notebox}{Static checking vs.\ intermediate code}
Static checking includes type checking and syntactic checks that the grammar cannot enforce (e.g., \texttt{break} must be inside a loop). Dragon Book Chapter 6 treats type checking and intermediate-code generation together, because both are done by attaching attributes and actions to the grammar.
\end{notebox}

\section{Variants of Syntax Trees and Intermediate Representations}
%====================================================================

\subsection{Syntax trees (abstract syntax trees)}
\label{sec:syntaxtree}
A \textbf{syntax tree} is a condensed form of the parse tree: operators and keywords appear as \emph{interior nodes}, and operands as children. Chains of single productions (such as $E\to T\to F\to\mathbf{id}$) disappear, and so do punctuation tokens such as parentheses. The tree keeps only what later phases need: \emph{which operation is applied to which operands}.

\begin{examplebox}{Example: parse tree vs.\ syntax tree for $a + b * c$}
Take the usual grammar $E \to E + T \mid T$, \ $T \to T * F \mid F$, \ $F \to \mathbf{id}$.

\subsection{Directed acyclic graphs (DAGs) for expressions}
A \textbf{DAG} identifies the \emph{common sub-expressions}: a node is shared if the same sub-expression appears more than once. It shows the same information as a syntax tree but is more compact, and it directly suggests how to generate efficient code that computes a common sub-expression only once.

\begin{examplebox}{Example: tree vs.\ DAG for $a + a*(b-c) + (b-c)*d$}
Figure~\ref{fig:treedag} shows the syntax tree (left) and the DAG (right). In the DAG, the leaf $a$ and the sub-expression $b-c$ are each shared by two parents.

\textbf{Why arrows?} A DAG is a \emph{directed} acyclic graph. Each edge points from an operator node to one of its operands (``this operation uses that value''), so a node with two incoming arrows is a value that is used twice. There is no cycle because an expression can never be an operand of itself. In a tree the direction is the same but is left implicit, since every node has exactly one parent.

\subsubsection{The value-number method for constructing DAGs}
\label{sec:vn}
\textbf{The problem.} While building the tree for an expression, we want to \emph{reuse} a node if the same sub-expression has already been built. To do this we need a fast way to answer: ``Have I already created a node for $b - c$?'' The \textbf{value-number method} gives a simple answer. Here we assume the \emph{syntax tree} of the expression has already been built (Figure~\ref{fig:treedag}(a)). We convert it into a DAG by visiting the tree nodes in \textbf{post-order} (left subtree, right subtree, then the node itself), so that the children of a node are always handled before the node.

\textbf{The idea.} Keep all nodes in an \textbf{array of records}. Each record describes one node of the DAG, and the \emph{position (index) of the record in the array is the node's value number}. The value number is therefore just the node's \emph{name}: ``node 4'' means ``the record at position 4''.

\begin{defbox}{What the numbers mean}
\begin{itemize}
\item \textbf{Value number} = the index of a record in the array = the identity of one DAG node. It is \emph{not} the numeric value of the expression (the number 4 does not mean the expression evaluates to 4).
\item A \textbf{leaf record} stores the kind of leaf and what it is: $(\mathbf{id},\ \text{pointer to symbol-table entry})$ for a variable, or $(\mathbf{num},\ \text{value})$ for a constant.
\item An \textbf{interior record} has the form $(\mathit{op},\ \mathit{left},\ \mathit{right})$. Here $\mathit{op}$ is the operator, and \textbf{\textit{left} and \textit{right} are the value numbers of the two child nodes}, i.e., they are \emph{pointers} to other records (the operands).
\end{itemize}
\end{defbox}

\textbf{Example.} The record $(*,\ 1,\ 4)$ means: ``a node for the operator $*$ whose left child is node~1 and whose right child is node~4''. Looking up the array, node 1 is the leaf $a$ and node 4 is $b - c$; so this record stands for $a * (b - c)$.

\begin{defbox}{Algorithm: finding or creating a node}
To create a node with signature $\langle \mathit{op},\ l,\ r\rangle$ (where $l$ and $r$ are value numbers of the children that were already created):
\begin{enumerate}[nosep]
\item \textbf{Search} the array for a record with exactly the same $\mathit{op}$, $\mathit{left}=l$, and $\mathit{right}=r$.
\item If such a record \textbf{exists}, do not create anything; \textbf{return its value number}. (This is the common sub-expression being shared.)
\item Otherwise \textbf{append} a new record $(\mathit{op},\ l,\ r)$ at the end of the array and \textbf{return its index} as the new value number.
\end{enumerate}
(For speed, a hash table keyed on $(\mathit{op},l,r)$ replaces the linear search in step 1.)
\end{defbox}

\textbf{Why does comparing only $(\mathit{op},l,r)$ work?} Two nodes represent the same expression exactly when they have the same operator and the same children. Children are the same exactly when they have the same value numbers (because every distinct sub-expression gets exactly one number). So, by building from the leaves upward, equal sub-expressions always get equal numbers.

\begin{examplebox}{A second example: $(a+b)*(a+b)$ and the commutativity trap}
Post-order requests and the records they create:
\begin{enumerate}[nosep]
\item leaf $a$ $\Rightarrow$ new record 1; \ leaf $b$ $\Rightarrow$ new record 2; \ $\langle +,1,2\rangle$ $\Rightarrow$ new record 3.
\item Second copy: leaf $a$ $\Rightarrow$ found (1); leaf $b$ $\Rightarrow$ found (2); $\langle +,1,2\rangle$ $\Rightarrow$ \textbf{found (3)}, shared.
\item $\langle *,3,3\rangle$ $\Rightarrow$ new record 4 (both children are the same node).
\end{enumerate}
The DAG has 4 nodes (the tree has 7) and gives \texttt{t1 = a + b}, \texttt{t2 = t1 * t1}. Note that the $*$ node has \emph{two} arrows into the same node: its left and its right operand are one and the same value.

\end{center} Now try $(a+b)*(b+a)$: the second sum is $\langle +,2,1\rangle$, which is \emph{not} equal to $\langle +,1,2\rangle$, so a new node is created and $a+b$ is computed twice. To avoid this, a compiler stores the children of a commutative operator in a canonical order (say, smaller value number first); then $\langle +,2,1\rangle$ becomes $\langle +,1,2\rangle$ and is shared.
\end{examplebox}

\begin{pitfallbox}{Limits of the method}
The test ``same $\mathit{op}$ and same children'' finds only \emph{syntactically identical} sub-expressions (up to the operand-order trick above). It does not know that $x*2$ and $x+x$ are equal; that needs algebraic simplification, a separate optimisation.
\end{pitfallbox}

\paragraph{Step-by-step example: $a + a*(b-c) + (b-c)*d$.}
We walk the syntax tree of Figure~\ref{fig:treedag}(a) in post-order: $a$, $a$, $b$, $c$, then $-$, $*$, $+$ of the left part, then $b$, $c$, $-$, $d$, $*$, and finally the root $+$. At every tree node we ask the array for the matching DAG node. Table~\ref{tab:vntrace} shows each request and what the algorithm does.

\paragraph{The whole procedure.} Converting a syntax tree into a DAG is a single post-order traversal:
\begin{lstlisting}
int buildDAG(TreeNode t) {            // returns a value number
    if (t is a leaf)
        return findOrCreateLeaf(t);   // search (id/num, entry); create if absent
    l = buildDAG(t.left);             // children first (post-order)
    r = buildDAG(t.right);
    return findOrCreateNode(t.op, l, r);   // search (op,l,r); create if absent
}
\end{lstlisting}
The ``search'' is only a \emph{lookup of an identical record} in the array (or hash table); it is not a second traversal of the tree.

\begin{notebox}{Looking ahead}
Building the tree first and then converting it is easy to understand. Later, after we study syntax-directed definitions (Section~\ref{sec:sdddag}), we will see that the same DAG can be built \emph{directly while parsing}, without constructing the tree at all: the parser simply calls the find-or-create routine each time it recognises an operator.
\end{notebox}

\subsection{Three-address code (TAC)}
In \textbf{three-address code} every instruction has \emph{at most one operator on the right side} and at most three addresses (two operands and one result). Compound expressions are broken into temporaries, so the order of evaluation is made explicit.

For $a + a*(b-c) + (b-c)*d$ the TAC (from the DAG, reusing $t_1 = b-c$) is:
\begin{lstlisting}
t1 = b - c
t2 = a * t1
t3 = a + t2
t4 = t1 * d
t5 = t3 + t4
\end{lstlisting}
Without the DAG (from the tree) $b-c$ would be computed twice.

\subsubsection{Generating three-address code from a DAG}\label{sec:tacdag}
\label{sec:dag2tac}
Three-address code can be generated from the DAG alone; no SDD or SDT is needed.

\paragraph{Idea.} Every \emph{interior} node of the DAG becomes exactly \emph{one} three-address instruction, with a fresh temporary holding its result. \emph{Leaves} generate no instruction: they only supply a name (a variable such as $a$, or a constant). A shared node is still one node, so it produces only one instruction; this is how the DAG removes the common sub-expression.

\paragraph{Order.} Process the records of the array in increasing order of value number. A node's children were always created before the node, so their value numbers are smaller, and their results are ready when the node is reached. The array order is therefore already a valid evaluation order.

\begin{lstlisting}
for i = 1 to n:                          // records in the array, in index order
    if record i is a leaf:
        name[i] = the variable or constant it stands for
    else:                                // record i = (op, left, right)
        name[i] = newTemp()
        emit( name[i] = name[left] op name[right] )
\end{lstlisting}
Here $\mathit{name}[i]$ is the address that holds the value of node $i$. For an assignment $x = \langle\text{expression}\rangle$ we finish with one more instruction, \texttt{x = name[root]}.

\paragraph{Three ways to obtain three-address code.}\label{par:threeways}
\begin{center}
\small
\begin{tabular}{@{}L{3.6cm} L{4.7cm} L{5.4cm}@{}}
\toprule
\textbf{Method} & \textbf{How} & \textbf{Common sub-expressions} \\ \midrule

\begin{notebox}{Caution: assignments inside the DAG}
If the DAG covers several statements and a variable is \emph{reassigned} in between (e.g., \texttt{a = a + 1}), a later use of $a$ is a different value and must not share the old leaf or any node built from it. Compilers handle this by creating a new leaf (a new value number) after each assignment. For single expressions, as in these notes, the issue does not arise.
\end{notebox}

\subsubsection{Representations of three-address code}
\label{sec:repr}
Three-address code is an \emph{abstract} language: it says \emph{what} the instructions are. A compiler also has to decide \emph{how to store} them in memory, as records in an array. There are two basic record layouts: \textbf{quadruples} and \textbf{triples}. Each of them represents the complete code on its own. (A third name, \emph{indirect triples}, is introduced at the end of this subsection; it is not a different representation of the code but an \emph{add-on to triples} that makes reordering cheap.)

Take the source statement $a = b * -c + b * -c$.

\paragraph{Indirect triples: triples plus an ordering list.} The disadvantage of triples shows up in optimisation, where the compiler often wants to \emph{reorder} instructions. Indirect triples fix it by separating two things that plain triples tie together: \emph{the triples themselves} (kept in a fixed array, numbered once and never renumbered) and \emph{the order of execution} (a separate list of pointers to triples). So indirect triples are not a new way of writing the code; they are triples with one extra list.

Quadruples are the simplest to reason about and to optimise, and are the usual textbook choice. Triples save space but are fragile under reordering. Indirect triples keep the compactness of triples and recover the flexibility of quadruples at the price of one extra list. All three encode exactly the same three-address code.
\end{notebox}

\subsubsection{Static single-assignment (SSA) form and the \texorpdfstring{$\varphi$}{phi}-function}
\label{sec:ssa}

\paragraph{The idea.} In \textbf{SSA form} every variable name is assigned in exactly one place in the program text. If the source assigns to the same variable several times, the compiler gives each assignment its own subscripted name. For straight-line code this is nothing more than renaming:
\begin{center}
\begin{minipage}[t]{0.40\textwidth}
\begin{lstlisting}
p = a + b
q = p - c
p = q * d
p = e - p
q = p + q
\end{lstlisting}
\end{minipage}\hfill
\begin{minipage}[t]{0.40\textwidth}
\begin{lstlisting}
p1 = a + b
q1 = p1 - c
p2 = q1 * d
p3 = e - p2
q2 = p3 + q1
\end{lstlisting}
\end{minipage}
\end{center}
On the right $p_1$, $p_2$, $p_3$ are three different values that happened to share the name $p$ on the left. Every \emph{use} now names exactly one \emph{definition}: the $p_3$ in the last line can only come from \texttt{p3 = e - p2}.

\begin{examplebox}{Why bother? One definition per name makes optimisation easy}
\begin{lstlisting}
a  = 1                a1 = 1
b  = a + 2            b1 = a1 + 2
a  = 10               a2 = 10
c  = a * b            c1 = a2 * b1
\end{lstlisting}
On the left, to fold \texttt{c = a * b} an optimiser must first find out \emph{which} of the two assignments to $a$ reaches that line (a data-flow analysis). On the right the question does not exist: $a_2$ has a single definition, \texttt{a2 = 10}; $b_1=a_1+2=3$; hence $c_1=10*3=30$. Once $a_1$ has no uses left, a quick count shows that \texttt{a1 = 1} is dead code and can be deleted. SSA turns ``which definition reaches here?'' into a lookup by name.
\end{examplebox}

\paragraph{The problem: two paths meet.} Straight-line code is easy. The difficulty starts where control flow \emph{joins}:
\begin{lstlisting}
if (flag) x = -1; else x = 1;
y = x * a;
\end{lstlisting}
Renaming the two assignments gives $x_1$ (in the \textbf{then}-branch) and $x_2$ (in the \textbf{else}-branch). But which name should \texttt{y = x * a} use? It depends on \texttt{flag}, which is known only at run time, so the compiler cannot choose at compile time. What we need is a \emph{new name} that means ``$x_1$ if we came through the \textbf{then}-branch, otherwise $x_2$''. That is exactly what the $\varphi$-function provides:
\[
x_3 = \varphi(x_1,\,x_2)
\]
\begin{lstlisting}
if (flag) x1 = -1; else x2 = 1;
x3 = phi(x1, x2);
y  = x3 * a;
\end{lstlisting}

\begin{center}
\begin{tikzpicture}[
  every node/.style={font=\small\ttfamily},
  b/.style={draw,rounded corners=2pt,minimum width=3.2cm,minimum height=0.8cm,fill=blue!6},
  e/.style={-{Stealth[length=2.3mm]},thick},
  lab/.style={font=\scriptsize\sffamily,fill=white,inner sep=1pt}]
 \node[b] (t) at (0,0) {if (flag)};
 \node[b,fill=green!12] (l) at (-2.6,-1.6) {x1 = -1};
 \node[b,fill=green!12] (r) at (2.6,-1.6) {x2 = 1};
 \node[b,fill=orange!18,minimum width=5.4cm,minimum height=1.1cm,align=center] (j) at (0,-3.4) {x3 = $\varphi$(x1, x2)\\ y = x3 * a};
 \draw[e] (t) -- node[lab,pos=0.5]{true} (l);
 \draw[e] (t) -- node[lab,pos=0.5]{false} (r);
 \draw[e] (l) -- node[lab,pos=0.55]{pred.\ 1} (j.north west);
 \draw[e] (r) -- node[lab,pos=0.55]{pred.\ 2} (j.north east);
 \node[font=\small\sffamily,anchor=west,align=left] at (4.3,-3.4) {$\varphi$ takes its\\ \emph{first} operand if\\ control came from\\ pred.\ 1, its \emph{second}\\ if it came from pred.\ 2};
\end{tikzpicture}
\end{center}

\begin{defbox}{What a $\varphi$-function is (and is not)}
\begin{itemize}[nosep]
\item It sits at the \emph{start} of a block that has two or more predecessors (a join point).
\item $v=\varphi(v_1,\dots,v_k)$ has one operand per predecessor, \emph{in the same order as the predecessors}. The value of $v$ is the operand that belongs to the edge along which control actually arrived.
\item If a block starts with several $\varphi$'s, they are evaluated \emph{simultaneously} on entry.
\item It is \textbf{not} an instruction that the machine executes and it does not test anything. It is notation that the compiler uses to keep ``one definition per name'' true at a join. It is removed again before machine code is generated (see below).
\end{itemize}
\end{defbox}

\paragraph{A loop: $\varphi$ at the loop header.} A loop is also a join: the header can be reached from before the loop (the first time) or from the end of the body (every later time). Take
\begin{lstlisting}
i = 0;  s = 0;
while (i < n) { s = s + i;  i = i + 1; }
return s;
\end{lstlisting}
The variables $i$ and $s$ both have different definitions arriving at the header, so both need a $\varphi$ there:

\begin{center}
\begin{tikzpicture}[
  every node/.style={font=\small\ttfamily},
  b/.style={draw,rounded corners=2pt,inner sep=4pt,align=left,fill=blue!6},
  e/.style={-{Stealth[length=2.3mm]},thick},
  lab/.style={font=\scriptsize\sffamily,fill=white,inner sep=1pt}]
 \node[b] (b0) at (0,0)    {\textbf{B0}\ \ i1 = 0\\ \phantom{\textbf{B0}}\ \ s1 = 0};
 \node[b,fill=orange!18] (b1) at (0,-2.4) {\textbf{B1}\ \ i2 = $\varphi$(i1, i3)\\ \phantom{\textbf{B1}}\ \ s2 = $\varphi$(s1, s3)\\ \phantom{\textbf{B1}}\ \ if i2 < n goto B2 else B3};
 \node[b,fill=green!12] (b2) at (6.6,-2.4) {\textbf{B2}\ \ s3 = s2 + i2\\ \phantom{\textbf{B2}}\ \ i3 = i2 + 1};
 \node[b] (b3) at (0,-4.8) {\textbf{B3}\ \ return s2};
 \draw[e] ([xshift=-0.9cm]b0.south) -- node[lab,pos=0.5]{pred.\ 1} ([xshift=-0.9cm]b1.north);
 \draw[e] (b1.east) -- node[lab]{true} (b2.west);
 \draw[e] (b2.north) .. controls +(0,1.6) and +(1.6,1.0) .. node[lab,pos=0.5]{pred.\ 2 (back edge)} ([xshift=1.2cm]b1.north);
 \draw[e] (b1.south) -- node[lab]{false} (b3.north);
\end{tikzpicture}
\end{center}
Both $\varphi$'s list the operand from B0 first (``pred.\ 1'') and the operand from B2 second (``pred.\ 2''). Note that $i_3$ and $s_3$ are used by the $\varphi$'s \emph{before} they are defined in program order; that is fine, because that operand is only chosen when control arrives from B2, i.e.\ after B2 has run. Trace for $n=2$:
\begin{center}
\small
\begin{tabular}{@{}c l c c c l@{}}
\toprule
\textbf{visit of B1} & \textbf{arrived from} & $i_2$ & $s_2$ & $i_2<2$? & \textbf{then B2 computes} \\ \midrule
1 & B0 (pred.\ 1) & $i_1=0$ & $s_1=0$ & yes & $s_3=0+0=0,\ \ i_3=1$ \\
2 & B2 (pred.\ 2) & $i_3=1$ & $s_3=0$ & yes & $s_3=0+1=1,\ \ i_3=2$ \\
3 & B2 (pred.\ 2) & $i_3=2$ & $s_3=1$ & no & leave loop: \texttt{return s2} $=1$ \\ \bottomrule
\end{tabular}
\end{center}
The result $1=0+1$ is the sum of $i$ over $i=0,1$, as the source program computes.

\paragraph{Where is a $\varphi$ needed?} Only at a join point, and only for a variable for which \emph{different definitions} arrive along different paths. A variable that has a single reaching definition needs no $\varphi$:
\begin{lstlisting}
y = 7;                          y1 = 7;
if (c) x = 1; else x = 2;       if (c) x1 = 1; else x2 = 2;
z = x + y;                      x3 = phi(x1, x2);   z1 = x3 + y1;
\end{lstlisting}
Here $x$ gets a $\varphi$ (two definitions meet) but $y$ does not (only $y_1$ reaches the join, along both paths). Compilers find the exact places with an algorithm based on \emph{dominance frontiers}, which is beyond these notes; the rule of thumb above is enough for exercises.

\paragraph{Leaving SSA.} Real processors have no $\varphi$ instruction. Before code generation each $\varphi$ is replaced by \emph{copies at the end of the predecessors}: for $x_3=\varphi(x_1,x_2)$ the first predecessor gets \texttt{x3 = x1} and the second gets \texttt{x3 = x2}. Often the register allocator gives $x_1$, $x_2$, $x_3$ the same register and the copies disappear.

\begin{pitfallbox}{Common confusions about SSA}
\begin{itemize}[nosep]
\item ``Single'' counts assignments in the \emph{program text}, not executions. In the loop above \texttt{i3 = i2 + 1} runs once per iteration, yet it is the only assignment to $i_3$ in the text.
\item $\varphi$ chooses by \emph{which edge control arrived on}, not by testing a condition or a value.
\item The order of the $\varphi$ operands must match the order of the predecessors. Swapping them silently gives a different program.
\item No $\varphi$ is needed for a variable that is not reassigned before the join.
\end{itemize}
\end{pitfallbox}

\subsection{What is an SDD, and what is it for?}
\label{sec:sddwhat}

\paragraph{Division of labour.} Up to now the course has used a \textbf{context-free grammar (CFG)}. A CFG together with a parser answers exactly two questions:
\begin{enumerate}[nosep]
\item \emph{Is this string a legal program?} (\textbf{syntax})
\item \emph{What is its structure?} The answer is the \textbf{parse tree}.
\end{enumerate}
That is all the CFG is needed for. Producing the parse tree is the job of \textbf{syntax analysis}, and the grammar alone is enough for it.

But a compiler must also know what the program \emph{means}, and a CFG cannot express this. For example, the parse tree of \texttt{3 * 5 + 4} shows that $3*5$ is grouped first, but nowhere does it contain the number 19. It also contains no machine or three-address instructions. Typical questions that the parse tree cannot answer are:
\begin{itemize}[nosep]
\item What is the \textbf{value} of this expression? \hfill (calculators, constant folding)
\item What is the \textbf{type} of this expression, and do the types fit together? \hfill (type checking)
\item Was this variable \textbf{declared} before it is used? \hfill (static checks, symbol table)
\item In which temporary or variable is its result \textbf{stored}, and which \textbf{instructions} implement this statement? \hfill (code generation)
\item To which \textbf{label} should control jump if this condition is true? \hfill (control flow)
\end{itemize}

\begin{examplebox}{Example: a program that is syntactically perfect but wrong}
\begin{lstlisting}
int x;
y = x + 1;
\end{lstlisting}
With a grammar such as $S\to\mathbf{id}=E\,;$ the second line is a legal statement, and the parser happily builds a parse tree for it. Yet the program is wrong, because $y$ was never declared. The grammar cannot say so: to detect the error, the compiler must look $y$ up in a \emph{symbol table}, and that table is information \emph{outside} the tree structure. (Formally, ``declared before use'' is not a context-free property.) The same applies to \texttt{int a; a = "hi";}: the grammar sees only \textbf{id} $=$ \textbf{string}, not that the types disagree.
\end{examplebox}

\paragraph{The solution: attach information to the tree.} A \textbf{syntax-directed definition (SDD)} is a CFG \emph{extended} with two things:
\begin{center}
\fbox{\parbox{0.88\textwidth}{\centering \textbf{SDD} \;=\; \textbf{CFG} \;+\; \textbf{attributes} (values stored on grammar symbols) \;+\; \textbf{semantic rules} (how to compute those values from the production used).}}
\end{center}
The CFG part is unchanged and still defines the syntax. The new parts add meaning. Applying the rules to a parse tree gives an \textbf{annotated parse tree}: the same tree with every node carrying its attribute values. ``Syntax-directed'' means that the computation is \emph{driven by the syntactic structure}: which rule fires at a node depends on which production was used there.

\begin{notebox}{Do real compilers build the parse tree?}
Usually not. The parse tree is a \emph{conceptual} object: it is the structure that the grammar assigns to the input, and it is what an SDD is defined on (annotated parse tree, dependency graph). A real parser seldom stores it:
\begin{itemize}[nosep]
\item A recursive-descent parser follows the derivation through its procedure calls, and an LR parser follows it through its stack and reductions. The tree is traversed implicitly, not built.
\item At each reduction (or procedure return) the parser executes the semantic actions, which is exactly the SDT idea. Typically these actions build a \textbf{syntax tree (AST)} node directly, e.g.\ $\at{E}{node}=\mathbf{new}\ \mathit{Node}(\tok{'+'},\at{E_1}{node},\at{T}{node})$ (Section~\ref{sec:sddtree}).
\end{itemize}
A parse tree has a node for every grammar symbol, including chain steps such as $E\to T\to F\to\mathbf{digit}$ and punctuation such as parentheses. A syntax tree keeps only the operators and operands that matter, so it is much smaller and is the usual input of the later phases (type checking, intermediate-code generation).

So the two statements fit together. \emph{Logically}, the CFG gives the structure and the SDD gives the meaning. \emph{In practice}, the parser's actions (an SDT) build the syntax tree directly and the full parse tree is never created. Later phases then evaluate attributes (for example types) over the syntax tree, which is attribute evaluation again, only on a different tree.
\end{notebox}

\paragraph{What is it used for?} To answer the common question directly: yes. A CFG with its parse tree is enough for \emph{syntax}; an SDD is the tool used to specify \emph{semantic analysis} and \emph{intermediate-code generation}, and related jobs:
\begin{center}
\small
\begin{tabular}{@{}L{4.0cm} L{4.8cm} L{5.4cm}@{}}
\toprule
\textbf{Task} & \textbf{Attribute computed} & \textbf{Compiler phase} \\ \midrule
Evaluate an expression & \textit{val} & calculators, constant folding \\
Check types, declarations & \textit{type}, symbol-table entry & semantic analysis \\
Build a syntax tree or DAG & \textit{node} (pointer) & front end, intermediate representation \\
Generate three-address code & \textit{addr}, \textit{code} & intermediate-code generation \\
Generate jumps for conditions & \textit{true}, \textit{false}, \textit{next} (labels) & intermediate-code generation \\ \bottomrule
\end{tabular}
\end{center}
Two remarks. First, the boundary between ``semantic analysis'' and ``code generation'' is blurred in practice, because one set of semantic rules often does both at once, for instance a rule that checks the types and emits a conversion in the same step. Second, an SDD is a general method, also used outside compilers (for example to evaluate expressions or to convert one data format to another).

\toprule

\textbf{What it is} & productions only & CFG + attributes + semantic rules & CFG + program fragments (\emph{actions}) in the bodies \\

\begin{notebox}{Do we need both SDD and SDT?}
No: they are \emph{two levels of description of the same translation}, not two separate tools used side by side.
\begin{itemize}[nosep]
\item The \textbf{SDD} is the \emph{specification}. It states what every attribute equals, e.g.\ $\at{E}{val}=\at{E_1}{val}+\at{T}{val}$, and fixes the \emph{dependencies}: an attribute can be computed only after the attributes it uses. This allows many evaluation orders, and the SDD does not choose among them.
\item The \textbf{SDT} is the \emph{implementation}. The same computation is written as an action inside the production, e.g.\ $E \to E_1 + T\ \{\ \at{E}{val}=\at{E_1}{val}+\at{T}{val}\ \}$, and therefore runs at one fixed point during parsing: the SDT \emph{chooses one} of the orders that the SDD allows.
\end{itemize}
Normally we first think in terms of an SDD (what should be computed?) and then turn it into an SDT (where do the actions go?). The SDD alone defines the meaning but is not yet a procedure; one can also write an SDT directly, but then the correct ordering is our own responsibility.

\textbf{So does an SDD say nothing about when?} It does say something, but only partially. The class of an SDD tells us which evaluation strategy is guaranteed to work: post-order for S-attributed, one left-to-right depth-first traversal for L-attributed, and a topological order of the dependency graph for any other non-circular SDD. These are the \emph{legal} orders. What the SDD cannot express is (i) the order of computations that do not depend on each other, which matters for side effects such as \textit{print}, \textit{gen} and \textit{addType}, and (ii) \emph{when during compilation} the work is done, for instance during parsing, without storing the tree. An SDT fixes both.
\end{notebox}

\subsection{Attributes}
An \textbf{attribute} is any value that we attach to a grammar symbol. It helps to picture the parse tree as a tree of \emph{records}: every node has the grammar symbol as its name plus a few fields (the attributes). If $X$ is a symbol and $a$ is an attribute, we write $X.a$ for the value of $a$ at a particular node labelled $X$. Attributes can be of any kind: numbers, strings, types, pointers to symbol-table entries, or even whole code sequences.

\paragraph{A note on the symbol names.} The letters $E, T, F, S, B$ used in this chapter have \emph{no special meaning in CFGs in general}. They are just names that the author of a particular grammar chose, by convention: $E$ for \emph{expression}, $T$ for \emph{term}, $F$ for \emph{factor}, $S$ for \emph{statement} and $B$ for \emph{boolean expression}. The expression grammar we use for examples is
\[
E \to E + T \mid T, \qquad T \to T * F \mid F, \qquad F \to (\,E\,) \mid \mathbf{digit},
\]
and a different grammar could use completely different names. Which attributes a symbol carries is likewise decided by the grammar designer, and an attribute exists only on the symbols for which it is declared (\at{E}{val} exists, but \at{B}{val} does not unless we define it).

\paragraph{Examples of attributes.} Typical attributes, with the symbols they are usually given in the grammars of this chapter, are:
\begin{itemize}[nosep]
\item \at{E}{val}: the numeric value of an expression ($E,T,F$ in the grammar above).
\item \at{E}{type}: the type of an expression (\texttt{int}, \texttt{float}, \dots).
\item \at{E}{addr}: the name or temporary that holds the result of the expression.
\item \at{E}{node}: a pointer to the syntax-tree node built for the expression.
\item \at{S}{code}: the three-address code generated for a statement (or expression).
\item \at{B}{true}, \at{B}{false}: the labels to jump to when a boolean expression is true or false.
\item \at{\mathbf{id}}{lexeme}: the actual characters of an identifier, supplied by the lexer.
\item \at{\mathbf{digit}}{lexval}: the numeric value of a number token, supplied by the lexer.
\end{itemize}

Different \emph{occurrences} of the same nonterminal in a production are distinguished by subscripts, e.g., in $E \to E_1 + T$ the $E$ on the left is the \emph{head} and $E_1$ is the $E$ in the body; both have a \textit{val}.

\subsection{Semantic rules: a first tiny example}
A \textbf{semantic rule} is attached to a production and says how to compute one attribute from other attributes \emph{of the symbols in that same production}. For the production $E \to E_1 + T$ the rule
\[
\at{E}{val} = \at{E_1}{val} + \at{T}{val}
\]
says: ``the value of the whole expression is the value of the left sub-expression plus the value of the term.'' Consider the grammar $E \to E + T \mid T,\ T \to \mathbf{digit}$, together with the rules
\begin{center}
\small
\begin{tabular}{@{}l l@{}}
\toprule
\textbf{Production} & \textbf{Semantic rule} \\ \midrule
$E \to E_1 + T$ & $\at{E}{val} = \at{E_1}{val} + \at{T}{val}$ \\
$E \to T$ & $\at{E}{val} = \at{T}{val}$ \\
$T \to \mathbf{digit}$ & $\at{T}{val} = \at{\mathbf{digit}}{lexval}$ \\ \bottomrule
\end{tabular}
\end{center}
Evaluate it on the input \texttt{2 + 3}. The parse tree is $E \Rightarrow E_1 + T$ with $E_1 \Rightarrow T \Rightarrow \mathbf{digit}(2)$ and $T \Rightarrow \mathbf{digit}(3)$. Working \emph{from the leaves upward}:
\begin{enumerate}[nosep]
\item The lexer supplies $\at{\mathbf{digit}}{lexval}=2$ and $3$.
\item $T \to \mathbf{digit}$ gives $\at{T}{val}=2$ (left) and $\at{T}{val}=3$ (right).
\item $E \to T$ gives $\at{E_1}{val}=2$.
\item $E \to E_1 + T$ gives $\at{E}{val}=2+3=5$.
\end{enumerate}
That is all an SDD does: it decorates the parse tree with attribute values by repeatedly applying the rules.

\subsection{Formal definition}
\begin{defbox}{Syntax-Directed Definition (SDD)}
A \textbf{syntax-directed definition} is a context-free grammar together with \textbf{attributes} attached to grammar symbols and \textbf{semantic rules} attached to productions. For a production $A \to \alpha$ every rule has the form
\[
b = f(c_1, c_2, \dots, c_k)
\]
where $f$ is a function and either
\begin{enumerate}[label=(\arabic*),nosep]
\item $b$ is a \textbf{synthesized} attribute of $A$ and $c_1,\dots,c_k$ are attributes of the symbols in $\alpha$ (the children), or other attributes of $A$ itself (allowed only if this creates no cycle); or
\item $b$ is an \textbf{inherited} attribute of a symbol $B$ in $\alpha$ and $c_1,\dots,c_k$ are attributes of $A$ (the parent) or of symbols in $\alpha$ (the siblings), or of $B$ itself.
\end{enumerate}
\end{defbox}

\subsection{Synthesized and inherited attributes}
\begin{notebox}{Analogy}
Think of the parse tree as a company. A \textbf{synthesized} attribute is a \emph{report sent up} to the manager: the manager's value is built from the reports of the subordinates (e.g., the value of $2+3$ is built from the values of $2$ and $3$). An \textbf{inherited} attribute is an \emph{instruction or information passed down or across}, from a parent or from siblings (e.g., the declared type \texttt{float} is passed down to every identifier in \texttt{float a, b, c}).
\end{notebox}

\begin{itemize}
\item A \textbf{synthesized attribute} at a parse-tree node $N$ is computed from attributes of $N$'s \emph{children}. (Occasionally it also uses another attribute of $N$ itself, e.g.\ $\at{A}{t}=\at{A}{s}+1$; this is allowed as long as there is no cycle.) Information flows \emph{bottom-up}. Terminals have synthesized attributes only (supplied by the lexer, e.g., \at{\mathbf{digit}}{lexval}).
\item An \textbf{inherited attribute} at $N$ is computed from attributes of $N$'s \emph{parent and siblings}. Information flows \emph{top-down / sideways}. Useful when the structure of the parse tree does not match the abstract syntax, e.g., passing a type to a list of identifiers, or passing the label to jump to.
\end{itemize}

\paragraph{How to read the figure (evaluation recipe).}
\begin{enumerate}[nosep]
\item The lexer supplies the \textit{lexval} of every \textbf{digit} leaf (3, 5, 4).
\item Each $F \to \mathbf{digit}$ copies it into \at{F}{val}; each $T \to F$ copies it up again.
\item $T \to T_1 * F$ is applied once both its children are known: $3 \times 5 = 15$.
\item $E \to E_1 + T$ then adds $15 + 4 = 19$, and $L \to E\,\mathbf{n}$ passes $19$ to the root.
\end{enumerate}
Every node is computed \emph{after} its children, i.e., in \textbf{post-order}. This is natural for synthesized attributes, and it is exactly the order in which an LR parser performs reductions.
\end{examplebox}

\begin{notebox}{Which evaluation order is needed?}
\begin{center}
\small
\begin{tabular}{@{}L{3.3cm} L{4.2cm} L{6cm}@{}}
\toprule
\textbf{Kind of SDD} & \textbf{Evaluation order} & \textbf{Dependency graph needed?} \\ \midrule
S-attributed (synthesized only) & post-order (children before parent), i.e.\ LR reductions & No: every edge points from child to parent, so post-order is already a topological order. \\
L-attributed & one depth-first, left-to-right traversal & No: inherited attributes depend only on the parent and left siblings. \\
General (arbitrary mix) & any topological order of the dependency graph & Yes: build the graph, topologically sort it, and reject it if it has a cycle. \\ \bottomrule
\end{tabular}
\end{center}
So the dependency graph with topological sort is the \emph{general} method; the two special classes are exactly those for which a fixed traversal makes it unnecessary.
\end{notebox}

\subsection{Annotated parse trees and dependency graphs}
An \textbf{annotated parse tree} shows the attribute values at every node. To evaluate attributes we build a \textbf{dependency graph}: one node per attribute instance, and an edge $x \to y$ whenever $y$ is computed from $x$. A valid evaluation order is any \emph{topological order} of this graph; if the graph has a cycle, no order exists.

\begin{notebox}{Which way do the arrows point?}
\textbf{Rule: the arrow goes from the attribute that is used to the attribute that is defined.} For a semantic rule $b = f(c_1,\dots,c_k)$ we draw an edge $c_i \to b$ for every $c_i$: the tail is on the \emph{right-hand side} of the rule (the input), the head is on the \emph{left-hand side} (the result). Reading an arrow $x\to y$ as ``$y$ needs $x$'' (so $x$ must be computed first) is what makes a topological order a valid evaluation order.

\textbf{Example.} Take the production $E \to L\ D$ with the rule $\at{D}{val} = \at{L}{val}$. The attribute defined is $\at{D}{val}$ and the attribute used is $\at{L}{val}$, so the edge is
\[
\at{L}{val}\ \longrightarrow\ \at{D}{val}.
\]
The arrow goes from the left sibling $L$ to the right sibling $D$, \emph{sideways} in the tree. Since $\at{D}{val}$ is defined by a rule of the production of its \emph{parent} $E$, it is an inherited attribute of $D$.

\begin{center}

\begin{tabular}{@{}L{4.2cm} L{4.6cm} L{4.2cm}@{}}
\toprule
\textbf{Rule (in production $A\to X\,Y$)} & \textbf{Edge} & \textbf{Direction in the tree} \\ \midrule
$\at{A}{s}=\at{X}{s}$ (synthesized) & $\at{X}{s}\to\at{A}{s}$ & child $\to$ parent (\emph{up}) \\
$\at{X}{i}=\at{A}{i}$ (inherited from parent) & $\at{A}{i}\to\at{X}{i}$ & parent $\to$ child (\emph{down}) \\
$\at{Y}{i}=\at{X}{s}$ (inherited from sibling) & $\at{X}{s}\to\at{Y}{i}$ & left sibling $\to$ right sibling (\emph{sideways}) \\ \bottomrule
\end{tabular}
\end{center}
A common mistake is to draw the arrow in the direction of the tree edge or to follow the ``flow of the parse''; always look at the rule instead: the arrow points \emph{into} the attribute on the left of the ``$=$''.
\end{notebox}

\begin{notebox}{A circular definition}
For $A \to B$ with the rules $\at{A}{s} = \at{B}{i} + 1$ and $\at{B}{i} = \at{A}{s} \times 2$, the value of \at{A}{s} needs \at{B}{i}, which needs \at{A}{s}. The dependency graph has a \emph{cycle}, so no evaluation order exists. A good SDD must be \emph{non-circular}; the classes S-attributed and L-attributed below guarantee this automatically.
\end{notebox}

\begin{notebox}{Side effects}
A semantic rule may also do something besides computing a value, e.g., \textit{addType}$(\mathit{entry},\,t)$ writes into the symbol table, \textit{print} writes to the output, and \textit{gen} emits an instruction. Such rules are called \textbf{side effects}; they are fine as long as the order in which they run does not change the result (or the order is controlled, which is the job of an SDT).
\end{notebox}

\subsection{Classes of SDDs that are easy to implement}

\begin{defbox}{S-attributed and L-attributed definitions}
\begin{itemize}
\item An SDD is \textbf{S-attributed} if \emph{every attribute is synthesized}. It can be evaluated in any bottom-up order, e.g., during LR parsing, at the time of reduction.
\item An SDD is \textbf{L-attributed} if each attribute is either synthesized, or inherited such that, for a production $A \to X_1 X_2 \cdots X_n$, the inherited attribute of $X_i$ depends only on:
 \begin{enumerate}[label=(\alph*),nosep]
 \item inherited attributes of $A$, and
 \item attributes (inherited or synthesized) of $X_1,\dots,X_{i-1}$ (the symbols to its \emph{left}), and
 \item attributes of $X_i$ itself, provided there is no cycle.
 \end{enumerate}
 Evaluation is possible in a single left-to-right depth-first traversal (e.g., during top-down/LL parsing).
\end{itemize}
Every S-attributed SDD is also L-attributed.
\end{defbox}

\begin{examplebox}{Not L-attributed}
For $A \to B\,C$, the rule $\at{C}{i} = \at{B}{s}$ is fine (the inherited attribute of $C$ uses its \emph{left} sibling $B$). But the rule $\at{B}{i} = f(\at{C}{x})$ makes the inherited attribute of $B$ depend on its \emph{right} sibling $C$, so the SDD is \emph{not} L-attributed.
\end{examplebox}

\subsection{More examples: L-attributed and general (non-circular) SDDs}
\label{sec:moresdd}
Most examples so far are S-attributed. Here are two examples with inherited attributes: one that is L-attributed, and one that is neither S- nor L-attributed, so that a dependency graph and a topological order are really needed.

\begin{notebox}{How to classify an SDD}
\begin{enumerate}[nosep]
\item Is every attribute synthesized? $\Rightarrow$ \textbf{S-attributed}: evaluate in post-order (LR reductions).
\item Otherwise, look at \emph{every inherited attribute} $X_i.a$ in a production $A\to X_1\cdots X_n$. Does its rule use only inherited attributes of $A$, attributes of $X_1,\dots,X_{i-1}$ (left siblings), or other attributes of $X_i$ itself? If this holds for all of them $\Rightarrow$ \textbf{L-attributed}: one depth-first left-to-right traversal suffices.
\item If some inherited attribute uses a \emph{right} sibling (or a synthesized attribute that would have to come from the right), the SDD is \textbf{not L-attributed}. Draw the dependency graph. If it has no cycle, the SDD is \textbf{non-circular} and any topological order evaluates it; if it has a cycle, the SDD is erroneous.
\end{enumerate}
\end{notebox}

\begin{examplebox}{Example 1 (L-attributed, not S-attributed): value of a binary fraction}
We evaluate a binary fraction such as \texttt{.101} $=\tfrac12+\tfrac18=0.625$. The weight of a bit depends on its \emph{position counted from the point}, which is passed \emph{down and to the right} as an inherited attribute \textit{pos}.
\begin{center}
\small
\begin{tabular}{@{}l l@{}}
\toprule
\textbf{Production} & \textbf{Semantic rules} \\ \midrule
$S \to \tok{'.'}\ L$ & $\at{L}{pos}=1;\quad \at{S}{val}=\at{L}{val}$ \\
$L \to B\ L_1$ & $\at{B}{pos}=\at{L}{pos};\quad \at{L_1}{pos}=\at{L}{pos}+1;\quad \at{L}{val}=\at{B}{val}+\at{L_1}{val}$ \\
$L \to \varepsilon$ & $\at{L}{val}=0$ \\
$B \to 0$ & $\at{B}{val}=0$ \\
$B \to 1$ & $\at{B}{val}=2^{-\at{B}{pos}}$ \\ \bottomrule
\end{tabular}
\end{center}
\textbf{Why L-attributed.} The inherited attributes are $\at{L}{pos}$, $\at{B}{pos}$ and $\at{L_1}{pos}$. In $L\to B\,L_1$, $\at{B}{pos}$ and $\at{L_1}{pos}$ use only $\at{L}{pos}$, the inherited attribute of the head, and in $S$ the rule for $\at{L}{pos}$ uses nothing. No inherited attribute depends on a symbol to its right. It is not S-attributed because \textit{pos} is inherited.

\textbf{Evaluation for \texttt{.101}.} A single depth-first left-to-right traversal works. Writing $L_a, L_b, L_c, L_d$ for the four occurrences of $L$ from left to right (so $L_a\to B_1L_b$, $L_b\to B_2L_c$, $L_c\to B_3L_d$, $L_d\to\varepsilon$):
\begin{center}
\small
\begin{tabular}{@{}c l l@{}}
\toprule
\textbf{Step} & \textbf{Rule used} & \textbf{Value} \\ \midrule
1 & $\at{L_a}{pos}=1$ \quad ($S\to\tok{'.'}L$) & $1$ \\
2 & $\at{B_1}{pos}=\at{L_a}{pos}$, \ $\at{L_b}{pos}=\at{L_a}{pos}+1$ & $1,\ 2$ \\
3 & $B_1\to1$: $\at{B_1}{val}=2^{-1}$ & $0.5$ \\
4 & $\at{B_2}{pos}=2$, \ $\at{L_c}{pos}=3$; \ $B_2\to0$: $\at{B_2}{val}=0$ & $0$ \\
5 & $\at{B_3}{pos}=3$, \ $\at{L_d}{pos}=4$; \ $B_3\to1$: $\at{B_3}{val}=2^{-3}$ & $0.125$ \\
6 & $L_d\to\varepsilon$: $\at{L_d}{val}=0$ & $0$ \\
7 & going back up: $\at{L_c}{val}=0.125+0$, \ $\at{L_b}{val}=0+0.125$, \ $\at{L_a}{val}=0.5+0.125$ & $0.625$ \\
8 & $\at{S}{val}=\at{L_a}{val}$ & $0.625$ \\ \bottomrule
\end{tabular}
\end{center}
\textbf{As an SDT.} Following the conversion rules of Section~\ref{sec:lattr}, each inherited attribute is computed by an action placed immediately before the symbol that uses it; this gives actions at the left end of a body and in the middle:
\begin{align*}
S &\to \tok{'.'}\ \{\ \at{L}{pos}=1\ \}\ L\ \{\ \at{S}{val}=\at{L}{val}\ \}\\
L &\to \{\ \at{B}{pos}=\at{L}{pos}\ \}\ B\ \{\ \at{L_1}{pos}=\at{L}{pos}+1\ \}\ L_1\ \{\ \at{L}{val}=\at{B}{val}+\at{L_1}{val}\ \}\\
  &\mid\ \varepsilon\ \{\ \at{L}{val}=0\ \}\\
B &\to 0\ \{\ \at{B}{val}=0\ \}\ \mid\ 1\ \{\ \at{B}{val}=2^{-\at{B}{pos}}\ \}
\end{align*}
\end{examplebox}

\begin{examplebox}{Example 2 (neither S- nor L-attributed, but non-circular): value of a binary integer}
Now evaluate an ordinary binary integer such as \texttt{101} $=5$. The weight of a bit is $2^{\textit{pos}}$ where \textit{pos} is the number of bits \emph{to its right}. This depends on the \emph{length of the rest of the string}, which is known only after the right part has been examined.
\begin{center}
\small
\begin{tabular}{@{}l l@{}}
\toprule
\textbf{Production} & \textbf{Semantic rules} \\ \midrule
$L \to B\ L_1$ & $\at{B}{pos}=\at{L_1}{len};\quad \at{L}{len}=\at{L_1}{len}+1;\quad \at{L}{val}=\at{B}{val}+\at{L_1}{val}$ \\
$L \to B$ & $\at{B}{pos}=0;\quad \at{L}{len}=1;\quad \at{L}{val}=\at{B}{val}$ \\
$B \to 0$ & $\at{B}{val}=0$ \\
$B \to 1$ & $\at{B}{val}=2^{\at{B}{pos}}$ \\ \bottomrule
\end{tabular}
\end{center}
\textbf{Classification.} \textit{pos} is inherited, so the SDD is not S-attributed. In $L\to B\,L_1$ the inherited attribute $\at{B}{pos}$ is computed from $\at{L_1}{len}$, an attribute of the \emph{right} sibling, so it is not L-attributed either: a left-to-right traversal reaches $B$ before it knows $\at{L_1}{len}$. It is nevertheless \emph{non-circular}: \textit{len} depends only on \textit{len} of the part below it, \textit{pos} depends only on \textit{len}, and \textit{val} depends on \textit{pos} and on \textit{val} further down. So we use a dependency graph.

\textbf{Dependency graph for \texttt{101}.} The parse tree is $L_a\to B_1L_b$, $L_b\to B_2L_c$, $L_c\to B_3$, with $B_1\to1$, $B_2\to0$, $B_3\to1$. Each box in Figure~\ref{fig:depgraph2} is one attribute instance with its final value; an arrow $x\to y$ means that $y$ is computed from $x$. The small red numbers give one valid topological order.

\textbf{Topological order (solution).}
\begin{enumerate}[nosep,label=(\arabic*)]
\item $\at{L_c}{len}=1$ and $\at{B_3}{pos}=0$ (rule $L\to B$; no dependence on anything).
\item $\at{B_3}{val}=2^{0}=1$ \ ($B_3\to1$), then $\at{L_c}{val}=1$.
\item $\at{L_b}{len}=\at{L_c}{len}+1=2$ and $\at{B_2}{pos}=\at{L_c}{len}=1$.
\item $\at{B_2}{val}=0$ \ ($B_2\to0$), then $\at{L_b}{val}=0+1=1$.
\item $\at{L_a}{len}=\at{L_b}{len}+1=3$ and $\at{B_1}{pos}=\at{L_b}{len}=2$.
\item $\at{B_1}{val}=2^{2}=4$ \ ($B_1\to1$), then $\at{L_a}{val}=4+1=5$.
\end{enumerate}
Other orders are also valid, e.g.\ all three \textit{len} values first. In practice a compiler evaluates such an SDD in \emph{several passes over the parse tree}: a bottom-up pass for \textit{len}, a top-down pass for \textit{pos}, and a bottom-up pass for \textit{val}.

\textbf{Remark.} The difficulty comes from the right-recursive grammar. With the left-recursive grammar $L\to L_1B\mid B$ and $\at{L}{val}=2\times\at{L_1}{val}+\at{B}{val}$ the same value is computed by an S-attributed SDD, with no \textit{pos} and no \textit{len}. Choosing the grammar well can remove the need for a dependency graph.
\end{examplebox}

\subsection{SDD for constructing syntax trees}
\label{sec:sddtree}

\paragraph{The goal.} The parser recognises an expression such as \texttt{a - 4 + c}. We want the compiler to end up with the \emph{syntax tree} of Section~\ref{sec:syntaxtree} in memory, with operators as interior nodes and operands as leaves. An SDD does this by attaching one synthesized attribute, \textit{node}, to every grammar symbol that stands for an expression.

\paragraph{The tools.} The attribute \at{E}{node} is a \emph{pointer} to the root of the (sub)tree that $E$ stands for. Two constructor functions create nodes and return a pointer to the new node:
\begin{itemize}[nosep]
\item $\mathbf{new}\ \mathit{Leaf}(\mathbf{id},\ \mathit{entry})$ \ or \ $\mathbf{new}\ \mathit{Leaf}(\mathbf{num},\ \mathit{val})$: creates a \emph{leaf} for an identifier (with a pointer to its symbol-table entry) or for a number (with its value);
\item $\mathbf{new}\ \mathit{Node}(op,\ \mathit{left},\ \mathit{right})$: creates an \emph{interior node} labelled $op$ whose two children are the nodes that the pointers \textit{left} and \textit{right} point to.
\end{itemize}

\paragraph{The SDD.} The grammar is $E\to E+T\mid E-T\mid T$, $T\to(E)\mid\mathbf{id}\mid\mathbf{num}$. The last column says whether the rule \emph{creates} a node or only \emph{passes a pointer upward}.
\begin{center}
\small
\begin{tabular}{@{}l l c@{}}
\toprule
\textbf{Production} & \textbf{Semantic rule} & \textbf{New node?} \\ \midrule
$E \to E_1 + T$ & $\at{E}{node} = \mathbf{new}\ \mathit{Node}(\tok{'+'},\ \at{E_1}{node},\ \at{T}{node})$ & yes (interior) \\
$E \to E_1 - T$ & $\at{E}{node} = \mathbf{new}\ \mathit{Node}(\tok{'-'},\ \at{E_1}{node},\ \at{T}{node})$ & yes (interior) \\
$E \to T$ & $\at{E}{node} = \at{T}{node}$ & no (copy) \\
$T \to (\,E\,)$ & $\at{T}{node} = \at{E}{node}$ & no (copy) \\
$T \to \mathbf{id}$ & $\at{T}{node} = \mathbf{new}\ \mathit{Leaf}(\mathbf{id},\ \at{\mathbf{id}}{entry})$ & yes (leaf) \\
$T \to \mathbf{num}$ & $\at{T}{node} = \mathbf{new}\ \mathit{Leaf}(\mathbf{num},\ \at{\mathbf{num}}{val})$ & yes (leaf) \\ \bottomrule
\end{tabular}
\end{center}
This is an S-attributed SDD: every rule computes the attribute of the head from the attributes of its body symbols. (If the grammar is made LL by eliminating left recursion, the same tree is built with an inherited attribute; see Section~\ref{sec:lattr}.)

\begin{defbox}{Recipe: building the tree by hand from an SDD}
Because this SDD is S-attributed (every attribute is synthesized), its rules can be evaluated by a \textbf{post-order traversal} of the parse tree, as in Section~\ref{sec:sddwhat}: visit the children from left to right, and only then the node itself.
\begin{enumerate}[nosep]
\item Draw the \textbf{parse tree} of the input.
\item Traverse it in \textbf{post-order}. When a node is visited, execute the semantic rule of its production.
\item A \textbf{leaf rule} ($T\to\mathbf{id}$, $T\to\mathbf{num}$) creates a leaf node. Give each newly created node the next name $p_1, p_2, p_3,\dots$ in the order of creation.
\item A \textbf{copy rule} ($E\to T$, $T\to(E)$) creates nothing: the pointer of the child is simply written on the parent.
\item An \textbf{operator rule} ($E\to E_1\pm T$) creates \emph{one} interior node. Its left child is the pointer of $E_1$, its right child is the pointer of $T$.
\item The \textit{node} of the root of the parse tree points to the finished syntax tree.
\end{enumerate}
Post-order guarantees that the children are visited before their parent, which is exactly what an operator rule needs: it uses the pointers of its operands. An LR parser reduces in the same post-order, so the same rules can also be run during parsing.
\end{defbox}

\textbf{Step 1: the annotated parse tree.} The input is the token string $\mathbf{id}\ \tok{-}\ \mathbf{num}\ \tok{+}\ \mathbf{id}$. Figure~\ref{fig:sddtree-parse} shows its parse tree. \begin{pitfallbox}{Common mistakes when building the tree}
\begin{itemize}[nosep]
\item \textbf{Creating a node for a copy rule.} $E\to T$ and $T\to(E)$ only pass a pointer upward. If your tree contains a node labelled $E$ or $T$, you have drawn the parse tree, not the syntax tree.
\item \textbf{Mixing up the children.} In $E\to E_1-T$ the left child is $\at{E_1}{node}$ and the right child is $\at{T}{node}$; for $a-4$ the order matters.
\item \textbf{Forgetting what post-order implies.} The first node created is the leftmost leaf, not the root; the root is visited, and its node created, last.
\end{itemize}
\end{pitfallbox}

\subsection{SDD for constructing DAGs directly}
\label{sec:sdddag}

\paragraph{The problem with the two-step method.} In Section~\ref{sec:vn} we first built the complete syntax tree and then walked over it in post-order to obtain the DAG. That works, but it builds a structure (the tree) that is thrown away immediately. An SDD lets us skip the tree: the parser creates DAG nodes \emph{while it parses}, and the tree never exists in memory.

\paragraph{The key observation.} The SDD of the previous subsection already has the right shape. Its rules for $E \to E_1 + T$ and $T \to T_1 * F$ create a node \emph{after} the nodes of the children are known, and a bottom-up parser performs reductions in exactly that (post-)order, which is also the order used by the value-number method. All we change is \emph{what the constructor functions do}:
\begin{itemize}[nosep]
\item In the tree SDD, $\mathbf{new}\ \mathit{Node}(op, l, r)$ \emph{always} allocates a fresh node.
\item In the DAG SDD, $\mathit{Node}(op, l, r)$ first \emph{searches} for an existing record with the same $(op, l, r)$ and allocates a new one only if there is none. $\mathit{Leaf}$ behaves in the same way.
\end{itemize}
Both functions return a \textbf{value number}, so the attribute $\at{E}{node}$ is now simply \emph{an integer: the index of the DAG node} (instead of a pointer to a tree node). The attribute rules themselves are unchanged.

\paragraph{The SDD.} To have a multiplication operator we use the usual three-level expression grammar ($E$ expression, $T$ term, $F$ factor), and a single synthesized attribute \textit{node}:
\begin{center}
\small
\begin{tabular}{@{}l l@{}}
\toprule
\textbf{Production} & \textbf{Semantic rule} \\ \midrule
$E \to E_1 + T$ & $\at{E}{node} = \mathit{Node}(\tok{'+'},\ \at{E_1}{node},\ \at{T}{node})$ \\
$E \to E_1 - T$ & $\at{E}{node} = \mathit{Node}(\tok{'-'},\ \at{E_1}{node},\ \at{T}{node})$ \\
$E \to T$ & $\at{E}{node} = \at{T}{node}$ \\
$T \to T_1 * F$ & $\at{T}{node} = \mathit{Node}(\tok{'*'},\ \at{T_1}{node},\ \at{F}{node})$ \\
$T \to F$ & $\at{T}{node} = \at{F}{node}$ \\
$F \to (\,E\,)$ & $\at{F}{node} = \at{E}{node}$ \\
$F \to \mathbf{id}$ & $\at{F}{node} = \mathit{Leaf}(\mathbf{id},\ \at{\mathbf{id}}{entry})$ \\
$F \to \mathbf{num}$ & $\at{F}{node} = \mathit{Leaf}(\mathbf{num},\ \at{\mathbf{num}}{val})$ \\ \bottomrule
\end{tabular}
\end{center}
The rules that only \emph{copy} a value ($E\to T$, $T\to F$, $F\to(E)$) create nothing: parentheses affect only the \emph{shape} of the DAG, they do not produce a node of their own. Only the rules containing $\mathit{Node}$ or $\mathit{Leaf}$ touch the array.

\paragraph{The two constructor functions.} The array of records and a hash table keyed on the \emph{signature} of a record are \emph{global data}, shared by all semantic rules for the whole input:
\begin{lstlisting}
record table[];                 // table[v] = record of the node with value number v
hash   index;                   // signature -> value number

int Leaf(kind, x) {             // kind is id or num; x is the entry or the value
    sig = (kind, x);
    if (index has sig) return index[sig];     // already exists: share it
    v = append(table, sig);                   // new record at the end
    index[sig] = v;
    return v;
}

int Node(op, l, r) {            // l and r are value numbers of the children
    sig = (op, l, r);
    if (index has sig) return index[sig];     // common sub-expression found
    v = append(table, sig);
    index[sig] = v;
    return v;
}
\end{lstlisting}
Compare with the \texttt{findOrCreate} routines of Section~\ref{sec:vn}: they are the same functions. The only new idea is \emph{who calls them}: the semantic rules of the grammar, not a tree-walking procedure.


\begin{notebox}{How does the SDD say ``tree'' or ``DAG''?}
The \emph{rules} cannot tell the difference: the DAG SDD above and the syntax-tree SDD of the previous subsection have the same productions, the same attribute \textit{node}, and the same dependency graph. Both are S-attributed. What differs is the \textbf{meaning of the constructor functions} that the rules call, and that is part of the definition of the SDD, in the same way that the meaning of \textit{gen} or \textit{addType} is:
\begin{itemize}[nosep]
\item $\mathbf{new}\ \mathit{Node}(op,l,r)$ \emph{always allocates} a fresh node. Equal sub-expressions get different nodes, so the result is a \textbf{syntax tree}.
\item $\mathit{Node}(op,l,r)$ \emph{looks for a record with the same $(op,l,r)$ first} and allocates only if none exists. Equal sub-expressions get the same node, so the result is a \textbf{DAG}.
\end{itemize}
So whoever writes the SDD must state which of the two is meant. In these notes we use the keyword $\mathbf{new}$ for ``always create'' and plain $\mathit{Node}$, $\mathit{Leaf}$ for ``find or create''. Nothing else changes: every later phase simply receives the attribute \textit{node} and does not care whether some nodes are shared (except that shared nodes need to be translated only once).
\end{notebox}

\begin{notebox}{Why this is a legitimate SDD}
$\mathit{Node}$ and $\mathit{Leaf}$ have a \emph{side effect} (they change the global table), which Section~\ref{sec:sddwhat} allowed under one condition: the order of the calls must not change the result. Here it is fixed by the dependencies: a parent's $\mathit{Node}$ call needs the value numbers of its children, so those calls are made first. The SDD is S-attributed, so it can be evaluated during LR parsing, with each rule executed at the reduction by which its production is recognised.
\end{notebox}

\begin{examplebox}{Example: input $(a+b)*(a+b)$}
The table lists the reductions in the order the parser performs them, but only those that call $\mathit{Leaf}$ or $\mathit{Node}$. The omitted reductions ($T\to F$, $E\to T$, $F\to(E)$) just copy the value number upward.
\begin{center}
\small
\begin{tabular}{@{}c l l l c@{}}
\toprule
\textbf{Step} & \textbf{Reduction} & \textbf{Call} & \textbf{Result} & \textbf{Value no.} \\ \midrule
1 & $F \to \mathbf{id}$ \ (first $a$) & $\mathit{Leaf}(\mathbf{id},a)$ & new record & 1 \\
2 & $F \to \mathbf{id}$ \ (first $b$) & $\mathit{Leaf}(\mathbf{id},b)$ & new record & 2 \\

Both methods therefore build the \emph{same DAG with the same value numbers}, and the final $\at{E}{node}=9$ identifies its root.

\paragraph{Two details.}
\begin{itemize}[nosep]
\item \textbf{Commutative operators.} If $\mathit{Node}$ stores the children of $+$ and $*$ in a canonical order (smaller value number first), then $a+b$ and $b+a$ are shared as well; without this, they are treated as different expressions (Section~\ref{sec:vn}).
\item \textbf{Generating code at the same time.} Whenever $\mathit{Node}$ \emph{creates} a record, it can also emit one three-address instruction for it, with a fresh temporary; when it \emph{finds} an existing record, it emits nothing. This is method~2 in the comparison of Section~\ref{sec:tacdag} (the paragraph ``Three ways to obtain three-address code''), and it produces code in which $b-c$ is computed only once.
\end{itemize}

\section{Syntax-Directed Translation Schemes (SDT)}
\label{sec:sdt}
%====================================================================

\subsection{From specification to implementation}
An SDD tells us \emph{what} every attribute must equal, but it does not say \emph{when} each rule should run. A real compiler, however, runs the rules \emph{while it is parsing}, in one definite order, and often without ever building the whole parse tree. A \textbf{syntax-directed translation scheme (SDT)} solves this: it takes the program fragments of the rules and writes them \emph{inside the production body, at the exact position where they should run}.

The same rule written both ways:
\begin{center}
\small
\begin{tabular}{@{}l l@{}}
\toprule
\textbf{SDD} (specification) & \textbf{SDT} (implementation) \\ \midrule
\begin{tabular}[t]{@{}l@{}}$E \to E_1 + T$\\ \ \ rule: $\at{E}{val} = \at{E_1}{val} + \at{T}{val}$\end{tabular}
&
$E \to E_1 + T\ \ \{\ \at{E}{val} = \at{E_1}{val} + \at{T}{val}\ \}$ \\ \bottomrule
\end{tabular}
\end{center}

\begin{center}
\small
\begin{tabular}{@{}L{3.2cm} L{5.6cm} L{5.6cm}@{}}
\toprule
 & \textbf{SDD} & \textbf{SDT} \\ \midrule
Nature & High-level specification: rules attached to productions & Concrete implementation: actions embedded in productions \\
Order of evaluation & Only constrained by the dependencies: any topological order is legal (post-order, left-to-right DFS, \dots{} depending on the class) & One explicit order: actions run in the left-to-right order of the production body, at the moment the parser reaches them \\
Rules/actions & Written next to the production & Written in braces $\{\dots\}$ inside the body \\
Used for & Designing and reasoning about the translation & Building the actual translator \\ \bottomrule
\end{tabular}
\end{center}

\subsection{Definition and the meaning of an action's position}
\begin{defbox}{Syntax-Directed Translation Scheme}
A \textbf{syntax-directed translation scheme} (SDT) is a context-free grammar with \textbf{program fragments} (\emph{semantic actions}) embedded within the production bodies, written in braces. The position of an action defines \emph{when} it is executed during parsing.
\[
B \to X\ \{a\}\ Y
\]
Here action $a$ is executed after $X$ has been recognised (and before $Y$).
\end{defbox}

\paragraph{How an SDT is executed.} Imagine the parse tree in which every action appears as an \emph{extra child}, exactly at the position where it is written in the production. Perform a \textbf{depth-first traversal from left to right}; whenever the traversal reaches an action, it is executed. Figure~\ref{fig:actiontree} shows this for a scheme that translates infix to postfix: \texttt{expr $\to$ expr + term \{print('+')\}\ |\ expr - term \{print('-')\}\ |\ term} and \texttt{term $\to$ digit \{print(digit)\}}.

   \draw[gray] (\a.south)--(\b.north);
 \node[anchor=west] at (-1.5,-5.6) {Output (actions visited left to right): \ \texttt{9\ 5\ -\ 2\ +}};
\end{tikzpicture}}

In practice the parser does not need to build this tree. A top-down parser executes an action at the corresponding point of its recursive-descent procedure. A bottom-up (LR) parser can only act when it \emph{reduces}: an action at the right end of a body runs at that reduction (a postfix SDT, next subsection), while an action in the middle of a body needs a marker nonterminal (Section~\ref{sec:marker}).

\subsection{Postfix translation schemes}
If the grammar is LR-parsable and the SDD is \textbf{S-attributed}, we can build an SDT with every action at the \emph{right end} of its production (a \textbf{postfix SDT}). The actions then execute at \emph{reduction time}, so the attribute of each grammar symbol can be stored beside it on the parser stack.

\begin{examplebox}{Postfix SDT for the desk calculator}
\begin{align*}
L &\to E\ \mathbf{n} &&\{\ \mathit{print}(\at{E}{val})\ \}\\
E &\to E_1 + T &&\{\ \at{E}{val} = \at{E_1}{val} + \at{T}{val}\ \}\\
E &\to T &&\{\ \at{E}{val} = \at{T}{val}\ \}\\
T &\to T_1 * F &&\{\ \at{T}{val} = \at{T_1}{val} \times \at{F}{val}\ \}\\
T &\to F &&\{\ \at{T}{val} = \at{F}{val}\ \}\\
F &\to (\,E\,) &&\{\ \at{F}{val} = \at{E}{val}\ \}\\
F &\to \mathbf{digit} &&\{\ \at{F}{val} = \at{\mathbf{digit}}{lexval}\ \}
\end{align*}
\end{examplebox}

\paragraph{Implementation on the LR parse stack.} Each stack entry holds a grammar symbol and its attribute value. When $A \to X Y Z$ is reduced, the actions read the values in the top three entries (\texttt{stack[top-2].val}, \texttt{stack[top-1].val}, \texttt{stack[top].val}), compute \at{A}{val}, pop three entries, and push $A$ with the new value.

\begin{center}
\small
\begin{tabular}{@{}l l l l@{}}
\toprule
\textbf{Stack (symbol:val)} & \textbf{Remaining input} & \textbf{Action} \\ \midrule
$\$$ & \texttt{3 * 5 + 4 n} & shift \\
$\$\ \mathbf{digit}{:}3$ & \texttt{* 5 + 4 n} & reduce $F\to\mathbf{digit}$ \\
$\$\ F{:}3$ & \texttt{* 5 + 4 n} & reduce $T\to F$ \\
$\$\ T{:}3$ & \texttt{* 5 + 4 n} & shift $*$, shift \textbf{digit} \\
$\$\ T{:}3\ *\ \mathbf{digit}{:}5$ & \texttt{+ 4 n} & reduce $F\to\mathbf{digit}$ \\
$\$\ T{:}3\ *\ F{:}5$ & \texttt{+ 4 n} & reduce $T\to T*F$ \quad ($3\times5=15$) \\
$\$\ T{:}15$ & \texttt{+ 4 n} & reduce $E\to T$ \\
$\$\ E{:}15$ & \texttt{+ 4 n} & shift $+$, shift \textbf{digit}, reduce to $T{:}4$ \\
$\$\ E{:}15\ +\ T{:}4$ & \texttt{n} & reduce $E\to E+T$ \quad ($15+4=19$) \\
$\$\ E{:}19$ & \texttt{n} & shift \textbf{n}, reduce $L\to E\,\mathbf{n}$, print 19 \\ \bottomrule
\end{tabular}
\end{center}

\subsection{Worked example: infix to postfix, written out completely}
\label{sec:infix2postfix}

\paragraph{The task.} In \textbf{infix} notation the operator stands between its operands (\texttt{a + b}); in \textbf{postfix} notation it stands \emph{after} them (\texttt{a b +}). Postfix needs no parentheses and no precedence rules: \texttt{a*(b+c)-d} becomes \texttt{a b c + * d -}, and a stack machine can execute it by pushing operands and letting each operator pop its two arguments. We translate with the usual three-level expression grammar, which already encodes precedence ($*,/$ bind tighter than $+,-$) and left associativity.

\paragraph{Step 1: the SDD.} Let every nonterminal have a string attribute $t$, the postfix form of the part of the input it derives. The operator is appended \emph{after} the strings of its two operands ($\cc$ means concatenation):
\begin{center}
\small
\begin{tabular}{@{}l l@{}}
\toprule
\textbf{Production} & \textbf{Semantic rule} \\ \midrule
$E \to E_1 + T$ & $\at{E}{t} = \at{E_1}{t}\cc\at{T}{t}\cc\tok{'+'}$ \\
$E \to E_1 - T$ & $\at{E}{t} = \at{E_1}{t}\cc\at{T}{t}\cc\tok{'-'}$ \\
$E \to T$       & $\at{E}{t} = \at{T}{t}$ \\
$T \to T_1 * F$ & $\at{T}{t} = \at{T_1}{t}\cc\at{F}{t}\cc\tok{'*'}$ \\
$T \to T_1 / F$ & $\at{T}{t} = \at{T_1}{t}\cc\at{F}{t}\cc\tok{'/'}$ \\
$T \to F$       & $\at{T}{t} = \at{F}{t}$ \\
$F \to (\,E\,)$ & $\at{F}{t} = \at{E}{t}$ \\
$F \to \mathbf{id}$  & $\at{F}{t} = \at{\mathbf{id}}{lexeme}$ \\
$F \to \mathbf{num}$ & $\at{F}{t} = \at{\mathbf{num}}{lexval}$ \\ \bottomrule
\end{tabular}
\end{center}
Every rule is S-attributed, so the SDD can be evaluated by a post-order traversal of the parse tree (or during LR parsing). Notice the special form of the rules: the string of the head is made of the strings of the body nonterminals \emph{in the same order}, with extra characters (the operators) inserted in between or appended. For such ``simple'' SDDs we do not have to build the long strings at all: we may print each piece \emph{at the moment it would have been appended}. That gives the SDT.

\paragraph{Step 2: the SDT.} Each rule is replaced by a $\mathit{print}$ action at the right end of the body. Since all actions are at the right end, this is a \textbf{postfix SDT} and an LR parser can run it. All productions are listed, including those that have no action.
\begin{align*}
E &\to E_1 + T &&\{\ \mathit{print}(\tok{'+'})\ \}\\
E &\to E_1 - T &&\{\ \mathit{print}(\tok{'-'})\ \}\\
E &\to T\\
T &\to T_1 * F &&\{\ \mathit{print}(\tok{'*'})\ \}\\
T &\to T_1 / F &&\{\ \mathit{print}(\tok{'/'})\ \}\\
T &\to F\\
F &\to (\,E\,)\\
F &\to \mathbf{id}  &&\{\ \mathit{print}(\at{\mathbf{id}}{lexeme})\ \}\\
F &\to \mathbf{num} &&\{\ \mathit{print}(\at{\mathbf{num}}{lexval})\ \}
\end{align*}
The rules $E\to T$, $T\to F$ and $F\to(E)$ print nothing: they only pass the work on. Operands are printed by the leaf rules, operators by the operator rules, and the position of the action explains the order: when $E\to E_1+T$ is reduced, $E_1$ and $T$ have already been reduced, so their output has already appeared and the $+$ comes after both.

\begin{examplebox}{Trace 1: \texttt{9-5+2} on the LR parse stack}
Nothing needs to be stored on the stack; the actions simply print. Read the last column to see the output grow.

\begin{notebox}{The position of the action decides the output}
Take $E\to E_1 + T$. With the action at the \emph{end}, after $T$, the operator is printed after both operands: \textbf{postfix}. If the action is moved into the \emph{middle}, between $E_1$ and $T$ (written $E\to E_1\ \{\mathit{print}(\tok{'+'})\}\ +\ T$), the operator is printed between its operands, and the same traversal gives back the \textbf{infix} order (without the parentheses). The grammar did not change; only the place of the action did. This is the whole point of an SDT: \emph{where} the action stands defines \emph{when} it runs. (An LR parser could run a middle action only through a marker nonterminal, Section~\ref{sec:marker}.)
\end{notebox}

\subsection{SDTs with actions inside productions}
When an action is in the middle of a production, it is performed \emph{immediately after all grammar symbols to its left have been matched}. A top-down parser does exactly that: the action is just a statement placed at that point of the recursive-descent procedure. An LR parser cannot: it only takes decisions at reductions, so a mid-production action must first be turned into a reduction using a marker nonterminal (Section~\ref{sec:marker}).

\begin{center}
\small
\begin{tabular}{@{}L{3.6cm} L{5.4cm} L{5.4cm}@{}}
\toprule
\textbf{Where the action is} & \textbf{Top-down (LL / recursive descent)} & \textbf{Bottom-up (LR)} \\ \midrule
At the right end & run after the last symbol of the body is matched & run at the reduction of the body \\
In the middle & run at that point of the procedure & not possible directly: introduce a marker $M\to\varepsilon$ \\ \bottomrule
\end{tabular}
\end{center}

\begin{examplebox}{Complete example: infix to postfix for a \emph{top-down} parser}
The postfix SDT of Section~\ref{sec:infix2postfix} uses left-recursive productions ($E\to E_1+T$), which a top-down parser cannot handle. To run the same translation in a recursive-descent parser, we remove the left recursion from the grammar \emph{and keep the actions where they belong}: each print action stays right after the operand it follows. (Why this rewriting works is explained step by step in Section~\ref{sec:leftrec}.)

\textbf{The simplest version: digits with $+$ and $-$.}
\begin{align*}
E &\to T\ R\\
R &\to +\ T\ \{\ \mathit{print}(\tok{'+'})\ \}\ R_1 \ \mid\ -\ T\ \{\ \mathit{print}(\tok{'-'})\ \}\ R_1 \ \mid\ \varepsilon\\
T &\to \mathbf{num}\ \{\ \mathit{print}(\at{\mathbf{num}}{lexval})\ \}
\end{align*}
Here $R$ stands for ``the rest of the expression'': zero or more groups of an operator followed by an operand. The action of $R\to+\,T\,\{\dots\}\,R_1$ comes \emph{after $T$ and before $R_1$}: the operand is printed first, then the operator, and only then the rest of the expression is handled. The production $R\to\varepsilon$ has no action: there is nothing left to print.

\textbf{Execution on \texttt{9-5+2}.} Figure~\ref{fig:topdownpost} shows the parse tree with each action as an extra child (dashed box). A depth-first, left-to-right visit executes the actions in the order of the bold numbers.

\textbf{As a recursive-descent parser.} A top-down parser has one procedure per nonterminal, and every action is simply a statement written at its position in the production. Here \texttt{look} is the current input symbol and \texttt{match(c)} consumes it.
\begin{lstlisting}
void E() { T(); R(); }

void R() {
    if (look == '+') { match('+'); T(); print('+'); R(); }
    else if (look == '-') { match('-'); T(); print('-'); R(); }
    else { /* R -> epsilon: do nothing */ }
}

void T() {
    if (isdigit(look)) { c = look; match(look); print(c); }
    else error();
}
\end{lstlisting}
Compare \texttt{R()} with the production: \texttt{match('+'); T(); print('+'); R();} is the body $+\ T\ \{\mathit{print}(\tok{'+'})\}\ R_1$ read from left to right.

\textbf{The complete scheme with $*$, $/$, parentheses and identifiers.} The same trick is repeated for the second precedence level. $R$ is the rest of an expression ($+,-$) and $Q$ is the rest of a term ($*,/$).
\begin{align*}
E &\to T\ R\\
R &\to +\ T\ \{\ \mathit{print}(\tok{'+'})\ \}\ R_1 \ \mid\ -\ T\ \{\ \mathit{print}(\tok{'-'})\ \}\ R_1 \ \mid\ \varepsilon\\
T &\to F\ Q\\
Q &\to *\ F\ \{\ \mathit{print}(\tok{'*'})\ \}\ Q_1 \ \mid\ /\ F\ \{\ \mathit{print}(\tok{'/'})\ \}\ Q_1 \ \mid\ \varepsilon\\
F &\to (\,E\,) \ \mid\ \mathbf{id}\ \{\ \mathit{print}(\at{\mathbf{id}}{lexeme})\ \}\ \mid\ \mathbf{num}\ \{\ \mathit{print}(\at{\mathbf{num}}{lexval})\ \}
\end{align*}
For \texttt{a*(b+c)-d} this scheme prints \texttt{abc+*d-}, the same output as the bottom-up scheme of Section~\ref{sec:infix2postfix}: $F$ prints \texttt{a}; $Q$ matches $*$, calls $F$, which parses $(b+c)$ and prints \texttt{bc+} inside; only then does $Q$ print \texttt{*}; finally $R$ matches $-$, $T$ prints \texttt{d}, and $R$ prints \texttt{-}.
\end{examplebox}


\begin{examplebox}{Worked example: actions in the middle of productions (declarations)}
We want to give every identifier in a declaration such as \texttt{float x, y} its type. The type is known only after $T$ has been parsed, and the identifiers must receive it \emph{as they are read}. This is why the actions cannot all stand at the end of a production.
\begin{align*}
D &\to T\ \mathbf{id}\ \{\ \at{L}{inh}=\at{T}{type};\ \mathit{addType}(\at{\mathbf{id}}{entry},\ \at{T}{type})\ \}\ L\\
T &\to \mathbf{int}\ \{\ \at{T}{type}=integer\ \}\ \mid\ \mathbf{float}\ \{\ \at{T}{type}=float\ \}\\
L &\to \tok{','}\ \mathbf{id}\ \{\ \mathit{addType}(\at{\mathbf{id}}{entry},\ \at{L}{inh});\ \at{L_1}{inh}=\at{L}{inh}\ \}\ L_1\ \mid\ \varepsilon
\end{align*}
The actions of $T$ are at the right end of their bodies, but the actions in $D$ and in $L$ are in the \emph{middle}: each is followed by the nonterminal ($L$ or $L_1$) that needs the inherited attribute it computes.

\textbf{Solution for \texttt{float x, y}.} Figure~\ref{fig:midaction} shows the parse tree with each action as an extra child. A depth-first traversal from left to right executes the actions in the order of the bold numbers.

\begin{enumerate}[nosep,label=(\arabic*)]
\item Reaching the end of $T\to\mathbf{float}$: $\at{T}{type}=float$.
\item Back in $D$, after $T$ and \textbf{id} (x) have been visited: $\at{L}{inh}=float$ and \textit{addType}$(x, float)$.
\item In $L$, after \texttt{,} and \textbf{id} (y): \textit{addType}$(y, float)$ and $\at{L_1}{inh}=float$. The remaining $L_1\to\varepsilon$ has no action.
\end{enumerate}
Result: the symbol table says $x:float$ and $y:float$.

\textbf{Why the position matters.} If the action of $D$ were written at the \emph{end}, after $L$, then $L$ would be processed before $\at{L}{inh}$ has a value, and \textit{addType}$(y,\dots)$ would use an undefined type. A mid-production action is therefore the way an SDT guarantees that an inherited attribute is computed \emph{before} the symbol that uses it. A top-down parser executes these actions as statements of its recursive-descent procedures; an LR parser needs marker nonterminals (Section~\ref{sec:marker}).
\end{examplebox}

\begin{examplebox}{Example: actions at the left end of a production body}
An action may be the very first item of a body. (An action cannot be attached to the head of a production; ``left'' here means the left end of the body.) Such an action runs \emph{before any symbol of the body is matched}, so it can use only the \emph{inherited} attributes of the head. The scheme below prints the nesting depth of every opening parenthesis of a balanced string; $P.d$ is an inherited attribute holding the depth of the current position.
\begin{align*}
S &\to \{\ \at{P}{d}=0\ \}\ P\\
P &\to \{\ \mathit{print}(\at{P}{d})\ \}\ \tok{'('}\ \{\ \at{P_1}{d}=\at{P}{d}+1\ \}\ P_1\ \tok{')'}\ \{\ \at{P_2}{d}=\at{P}{d}\ \}\ P_2\ \ \mid\ \ \varepsilon
\end{align*}
Here the first action of $S$ \emph{initialises} the inherited attribute of $P$, and the first action of $P$ \emph{reads} $\at{P}{d}$, which was set by an action before $P$ was entered. For the input \texttt{(()())} the output is \texttt{0 1 1}.
\end{examplebox}

\subsection{Marker nonterminals (actions in the middle, for bottom-up parsing)}
\label{sec:marker}
Suppose an action must appear in the middle of a production, e.g., $B \to X\ \{a\}\ Y$. For an LR parser we replace the action by a \textbf{marker nonterminal} $M$ with an empty production:
\[
B \to X\ M\ Y, \qquad M \to \varepsilon\ \{a\}
\]
The action $a$ is then executed upon reducing $M \to \varepsilon$, which happens exactly when $X$ is on top of the stack and $Y$ has not been read yet.

\begin{examplebox}{Example: the infix-to-postfix scheme under LR parsing}
The top-down scheme $R \to +\ T\ \{\mathit{print}(\tok{'+'})\}\ R_1$ has its action in the middle. For an LR parser we write
\[
R \to +\ T\ M\ R_1, \qquad M \to \varepsilon\ \{\ \mathit{print}(\tok{'+'})\ \}
\]
When $M\to\varepsilon$ is reduced, the operand $T$ has just been reduced (and printed), so the output order is unchanged: $9\,5\,-\,2\,+$ for \texttt{9-5+2}. (This example only illustrates the marker technique. For this translation an LR parser would not use markers at all: the left-recursive postfix SDT of Section~\ref{sec:infix2postfix} has every action at the right end of its body.)
\end{examplebox}

\begin{pitfallbox}{Markers can create conflicts}
A marker forces the parser to decide to reduce $M\to\varepsilon$ \emph{before} it knows which production will finally be used. If two productions start with the same symbols, say $S\to X\,M\,Y \mid X\,Z$, the parser must choose, using only the next input token, whether to reduce $M$. If $Y$ and $Z$ can start with the same token, the result is a conflict and the grammar is no longer LR(1). The markers in backpatching ($M$ before a statement, $N$ before \textbf{else}) are safe because they always occur at a point where the parser can already tell what is coming.
\end{pitfallbox}

We will use markers $M$ and $N$ extensively in backpatching (Section~\ref{sec:backpatch}).

\subsection{Eliminating left recursion from an SDT}
\label{sec:leftrec}

We go in three small steps: (1) why a top-down parser needs a different grammar, (2) the change of the grammar alone, and (3) how the actions must change with it. The running example is the grammar for sums and differences, $E\to E_1+T\mid E_1-T\mid T$.

\begin{defbox}{Two forms of the same question: SDD or SDT}
An exam may ask you to remove left recursion from an \textbf{SDD} or from an \textbf{SDT}. The work is the same; only the way the semantic rules are written differs.
\begin{enumerate}[nosep]
\item \textbf{Rewrite the grammar} (Step 2 below). This is identical in both forms.
\item \textbf{Rewrite the attribute rules.} The new nonterminal $R$ gets an inherited attribute $R.i$ (the result so far) and a synthesized attribute $R.s$ (the final result). The base case initialises $R.i$; each repeated group updates it and passes it to $R_1.i$; $R\to\varepsilon$ copies $R.i$ into $R.s$; the head copies $R.s$ upward. The outcome is an \textbf{SDD}.
\item \textbf{Place the rules inside the productions} (SDT only). Each rule becomes an action in braces: an action that computes an inherited attribute of a symbol goes \emph{immediately before} that symbol, and an action that computes a synthesized attribute of the head goes at the \emph{end} of the body (Section~\ref{sec:lattr}). The outcome is an \textbf{SDT}.
\end{enumerate}
\begin{center}
\small
\begin{tabular}{@{}l p{4.6cm} p{5.6cm}@{}}
\toprule
 & \textbf{Answer as an SDD} & \textbf{Answer as an SDT} \\ \midrule
Semantic rules are written & as equations next to each production & as $\{\dots\}$ actions inside the body \\
Does position matter? & no & yes: inherited attribute before the symbol, synthesized attribute of the head at the end \\
Kind of SDD & L-attributed ($R.i$ is inherited) & the same L-attributed SDD, with its rules placed in the bodies \\
Evaluated by & depth-first, left-to-right traversal & the parser, as it parses (e.g.\ recursive descent) \\ \bottomrule
\end{tabular}
\end{center}
\textbf{Checklist for a full-marks answer:} (a) the new grammar without left recursion; (b) the attributes of the new nonterminal, stating which is inherited and which synthesized; (c) the base-case rule that initialises $R.i$; (d) the update rule for $R_1.i$; (e) the rule $R.s=R.i$ for $\varepsilon$; (f) the rule that copies $R.s$ to the head; (g) for an SDT only, the actions in the correct positions; (h) if an input is given, a trace of $R.i$ and $R.s$.
\end{defbox}

\paragraph{Step 1: why bother?} A top-down (recursive-descent) parser has one procedure per nonterminal, and it chooses a production by looking at the next input token. For a left-recursive production the procedure would have to start by calling \emph{itself}:
\begin{lstlisting}
void E() {            // for  E -> E + T
    E();              // calls E() again before reading any token ...
    match('+'); T();  // ... so this line is never reached: infinite recursion
}
\end{lstlisting}
No input is consumed between the two calls, so the parser loops forever. A grammar is \textbf{left-recursive} when a nonterminal can derive a string that starts with itself, as in $A\to A\,\alpha$. Top-down parsers need that rule rewritten; LR parsers do not (they handle left recursion happily, which is why the postfix SDT of Section~\ref{sec:infix2postfix} could use $E\to E_1+T$).

\paragraph{Step 2: change the grammar (no actions yet).} What does $E\to E+T\mid T$ generate? Just a $T$ followed by any number of ``$+\,T$'' groups: $T$, \ $T+T$, \ $T+T+T$, \dots{} So we can write the same language directly, left to right:
\begin{center}
\small
\begin{tabular}{@{}l l@{}}
\toprule
\textbf{Left-recursive} & \textbf{Right-recursive (no left recursion)} \\ \midrule
$E \to E + T \mid T$ & $E \to T\ R$ \\
 & $R \to +\ T\ R \mid \varepsilon$ \\ \bottomrule
\end{tabular}
\end{center}
$R$ means ``the rest'': zero or more groups of $+\,T$. Both grammars derive the same string $T+T+T$; only the \emph{order of growth} differs:
\begin{align*}
\text{left-recursive:}\quad & E \Rightarrow E+T \Rightarrow E+T+T \Rightarrow T+T+T\\
\text{right-recursive:}\quad & E \Rightarrow T\,R \Rightarrow T+T\,R \Rightarrow T+T+T\,R \Rightarrow T+T+T
\end{align*}
In the first derivation the string grows to the left (the first $T$ is produced last); in the second it grows from left to right, the way we read it.

\begin{defbox}{Recipe: removing immediate left recursion (grammar only)}
\[
A \to A\,\alpha \mid \beta
\qquad\text{becomes}\qquad
A \to \beta\,R, \qquad R \to \alpha\,R \mid \varepsilon .
\]
$\beta$ is what $A$ can start with, and $\alpha$ is what may be repeated after it. With several alternatives, $E\to E+T\mid E-T\mid T$ gives $E\to T\,R$, \ $R\to +\,T\,R\mid -\,T\,R\mid\varepsilon$.
\end{defbox}

\begin{pitfallbox}{The tempting wrong fix}
Why not make the grammar right-recursive in the obvious way, $E\to T-E_1\mid T+E_1\mid T$, and keep the rules $E.val=T.val\pm E_1.val$? The grammar is fine, but the meaning is wrong: for \texttt{9-5+2} we get $9-(5+2)=2$ instead of $(9-5)+2=6$. The tree now groups to the right, and subtraction is not associative. The translation must keep the \emph{left} grouping even though the tree leans right.
\end{pitfallbox}

\paragraph{The idea: carry a running total.} Think of a pocket calculator. You key in 9, then press ``$-5$'' (display shows 4), then ``$+2$'' (display shows 6). You never needed the whole expression; the display always holds \emph{the result so far}. We give $R$ exactly this display:
\begin{itemize}[nosep]
\item $R.i$ (\emph{inherited}, handed down from the left) is the result \textbf{so far} when $R$ starts;
\item $R.s$ (\emph{synthesized}, handed back up) is the \textbf{final result} when $R$ is finished.
\end{itemize}
Each rule of the old grammar finds its place in the new one:
\begin{enumerate}[nosep]
\item The \textbf{base case} $E\to T$ starts the display: $R.i=T.val$.
\item Each \textbf{repeated group} $+\,T$ or $-\,T$ updates the display and passes it to the next $R$: $R_1.i=R.i\pm T.val$.
\item The \textbf{end} $R\to\varepsilon$ has nothing more to read, so the display is the answer: $R.s=R.i$. The answer is then copied upward through every $R$ to $E$.
\end{enumerate}

\begin{defbox}{General transformation, SDD form (equations only)}
\begin{center}
\small
\begin{tabular}{@{}l l@{}}
\toprule
\textbf{Left-recursive SDD} & \\ \midrule
$A \to A_1\,Y$ & $\at{A}{a}=g(\at{A_1}{a},\ \at{Y}{y})$ \\
$A \to X$      & $\at{A}{a}=f(\at{X}{x})$ \\ \midrule
\textbf{After removing left recursion} & \\ \midrule
$A \to X\,R$   & $\at{R}{i}=f(\at{X}{x})$; \ $\at{A}{a}=\at{R}{s}$ \\
$R \to Y\,R_1$ & $\at{R_1}{i}=g(\at{R}{i},\ \at{Y}{y})$; \ $\at{R}{s}=\at{R_1}{s}$ \\
$R \to \varepsilon$ & $\at{R}{s}=\at{R}{i}$ \\ \bottomrule
\end{tabular}
\end{center}
$\at{R}{i}$ is inherited and $\at{R}{s}$ is synthesized. There are no braces and no order of writing; the dependencies alone fix the order of evaluation. The SDD is now L-attributed, not S-attributed.
\end{defbox}

\begin{defbox}{General transformation, SDT form (actions inside the body)}
\begin{align*}
A &\to A_1\,Y\ \{\ \at{A}{a}=g(\at{A_1}{a},\ \at{Y}{y})\ \}\ \mid\ X\ \{\ \at{A}{a}=f(\at{X}{x})\ \}
\intertext{becomes}
A &\to X\ \{\ \at{R}{i}=f(\at{X}{x})\ \}\ R\ \{\ \at{A}{a}=\at{R}{s}\ \}\\
R &\to Y\ \{\ \at{R_1}{i}=g(\at{R}{i},\ \at{Y}{y})\ \}\ R_1\ \{\ \at{R}{s}=\at{R_1}{s}\ \}\ \mid\ \varepsilon\ \{\ \at{R}{s}=\at{R}{i}\ \}
\end{align*}
$R.i$ (inherited) carries the value accumulated \emph{so far}; $R.s$ (synthesized) carries the final result back to the top. In the sum example $f$ is the identity and $g$ is $+$ or $-$.
\end{defbox}

\subsection{Converting an L-attributed SDD into an SDT}
\label{sec:lattr}
\begin{defbox}{Rules for converting an L-attributed SDD to an SDT}
\begin{enumerate}[nosep]
\item \textbf{Inherited attribute} of a nonterminal $X$ in the body: embed the action that computes it \emph{immediately before} $X$ in the body. If several inherited attributes of $X$ depend on one another, order the actions appropriately.
\item \textbf{Synthesized attribute} of the head $A$: place the action that computes it at the \emph{end} of the production body.
\end{enumerate}
\end{defbox}

\begin{examplebox}{Example: syntax tree for a left-recursion-free grammar}
After removing left recursion from $E \to E_1 + T \mid E_1 - T \mid T$ (the SDD form of these rules is Example~2 of Section~\ref{sec:leftrec}):
\begin{align*}
E &\to T\ \{\ \at{R}{i} = \at{T}{node}\ \}\ R\ \{\ \at{E}{node} = \at{R}{s}\ \}\\
R &\to +\ T\ \{\ \at{R_1}{i} = \mathbf{new}\ \mathit{Node}(\tok{'+'},\at{R}{i},\at{T}{node})\ \}\ R_1\ \{\ \at{R}{s} = \at{R_1}{s}\ \}\\
R &\to -\ T\ \{\ \at{R_1}{i} = \mathbf{new}\ \mathit{Node}(\tok{'-'},\at{R}{i},\at{T}{node})\ \}\ R_1\ \{\ \at{R}{s} = \at{R_1}{s}\ \}\\
R &\to \varepsilon\ \{\ \at{R}{s} = \at{R}{i}\ \}\\
T &\to \mathbf{id}\ \{\ \at{T}{node} = \mathbf{new}\ \mathit{Leaf}(\mathbf{id},\at{\mathbf{id}}{entry})\ \}\\
T &\to \mathbf{num}\ \{\ \at{T}{node} = \mathbf{new}\ \mathit{Leaf}(\mathbf{num},\at{\mathbf{num}}{val})\ \}
\end{align*}
Here $R.i$ (inherited) carries the tree built \emph{so far}; $R.s$ (synthesized) returns the final tree. For \texttt{a - 4 + c} the tree $((a - 4) + c)$ is produced with the correct left-associativity.

\textbf{Trace for \texttt{a - 4 + c}.} Now the ``running total'' is a \emph{pointer to the tree built so far}. The nodes are named $p_1,\dots,p_5$ in the order of creation, exactly as in Section~\ref{sec:sddtree}.
\begin{center}
\small
\begin{tabular}{@{}l c l L{5.6cm} c@{}}
\toprule
\textbf{Call} & $R.i$ \textbf{on entry} & \textbf{Next input} & \textbf{Action} & $R.s$ \textbf{on return} \\ \midrule
$E\to T\,R$ & --- & \texttt{a} & $T.node = p_1$ (leaf $a$); \ $R.i = p_1$ & --- \\
$R$ (1st) & $p_1$ & \texttt{- 4} & $T.node = p_2$ (leaf 4); \ $R_1.i = \mathbf{new}\ \mathit{Node}(\tok{'-'},p_1,p_2) = p_3$ & $p_5$ \\
$R_1$ (2nd) & $p_3$ & \texttt{+ c} & $T.node = p_4$ (leaf $c$); \ $R_2.i = \mathbf{new}\ \mathit{Node}(\tok{'+'},p_3,p_4) = p_5$ & $p_5$ \\
$R_2$ (3rd) & $p_5$ & end & $\varepsilon$: \ $R_2.s = R_2.i = p_5$ & $p_5$ \\ \bottomrule
\end{tabular}
\end{center}
The same five nodes are created in the same order as with the left-recursive SDD, so the syntax tree is identical (Figure~\ref{fig:sddtree-grow}); only the way the pointer travels differs: it is handed down in $R.i$ and returned in $R.s$.
\end{examplebox}

\subsection{Application: the structure of a type (array types)}
\label{sec:typestruct}

\paragraph{The task.} A declaration such as \texttt{int [2][3]} must be turned into a \textbf{type expression}: the array type \textit{array}$(2,\ \textit{array}(3,\ \mathit{integer}))$, an array of 2 elements, each of which is an array of 3 integers. The compiler later uses this tree to compute sizes and offsets (Section~\ref{sec:exprtac}) and to check types.

\paragraph{The grammar.} $T\to B\,C$, \ $B\to\mathbf{int}\mid\mathbf{float}$, \ $C\to\tok{[}\,\mathbf{num}\,\tok{]}\,C_1\mid\varepsilon$. The nonterminal $B$ is the basic type and $C$ is the (possibly empty) list of dimensions.

\paragraph{The SDD.} The basic type $B.t$ is known at the \emph{left}, but it has to end up at the \emph{bottom} of the array type, where the last dimension is. So we pass it down in an inherited attribute $C.b$ (``base'') and build the type on the way back up in the synthesized attribute $C.t$.
\begin{center}
\small
\begin{tabular}{@{}l l@{}}
\toprule
\textbf{Production} & \textbf{Semantic rules} \\ \midrule
$T \to B\,C$ & $\at{T}{t}=\at{C}{t}$; \ $\at{C}{b}=\at{B}{t}$ \\
$B \to \mathbf{int}$ & $\at{B}{t}=\mathit{integer}$ \\
$B \to \mathbf{float}$ & $\at{B}{t}=\mathit{float}$ \\
$C \to \tok{[}\,\mathbf{num}\,\tok{]}\,C_1$ & $\at{C}{t}=\mathit{array}(\at{\mathbf{num}}{val},\ \at{C_1}{t})$; \ $\at{C_1}{b}=\at{C}{b}$ \\
$C \to \varepsilon$ & $\at{C}{t}=\at{C}{b}$ \\ \bottomrule
\end{tabular}
\end{center}
$B.t$, $C.t$ and $T.t$ are synthesized; $C.b$ is inherited. The SDD is \textbf{L-attributed}: $C.b$ of $C$ depends on its left sibling $B$, and $C_1.b$ depends on the inherited attribute of its parent. It is not S-attributed, because the base type has to travel \emph{downward}.

\begin{examplebox}{Example: the type of \texttt{int [2][3]}}
The parse tree and the values of the attributes are in Figure~\ref{fig:typetree}.

\paragraph{As an SDT.} Following the rules of Section~\ref{sec:lattr}, the action that computes the inherited attribute $C.b$ goes immediately before $C$, and the actions that compute synthesized attributes go at the end:
\begin{align*}
T &\to B\ \{\ \at{C}{b}=\at{B}{t}\ \}\ C\ \{\ \at{T}{t}=\at{C}{t}\ \}\\
B &\to \mathbf{int}\ \{\ \at{B}{t}=\mathit{integer}\ \}\ \mid\ \mathbf{float}\ \{\ \at{B}{t}=\mathit{float}\ \}\\
C &\to \tok{[}\ \mathbf{num}\ \tok{]}\ \{\ \at{C_1}{b}=\at{C}{b}\ \}\ C_1\ \{\ \at{C}{t}=\mathit{array}(\at{\mathbf{num}}{val},\ \at{C_1}{t})\ \}\ \mid\ \varepsilon\ \{\ \at{C}{t}=\at{C}{b}\ \}
\end{align*}
The grammar is right-recursive, so a top-down parser can use it directly; no left recursion has to be removed. Section~\ref{sec:impl-lattr} turns it into a recursive-descent parser.

\begin{pitfallbox}{Why not synthesized attributes only?}
Suppose we try $C\to\tok{[}\mathbf{num}\tok{]}\,C_1$ with $C.t=\mathit{array}(num.val,\ C_1.t)$ and $C\to\varepsilon$ with $C.t=B.t$. The base type of $B$ is not visible inside $C$ (it is a sibling of $C$'s parent), so $C\to\varepsilon$ cannot read it. This is exactly why the inherited attribute $C.b$ is needed: it carries $B.t$ down to the place where it is used.
\end{pitfallbox}

\subsection{Implementing L-attributed SDDs during top-down parsing}
\label{sec:impl-lattr}

An L-attributed SDD can be evaluated in a single left-to-right depth-first traversal, which is exactly the order in which a top-down parser works. So an SDT for an L-attributed SDD can be executed \emph{while parsing}, without building the parse tree. There are three ways to do this with a top-down parser; they differ in where the attribute values are kept.

\begin{center}
\small
\begin{tabular}{@{}l p{4.2cm} p{6.4cm}@{}}
\toprule
\textbf{Method} & \textbf{Parser} & \textbf{Where attributes live} \\ \midrule
A. Arguments and return values & recursive descent & inherited attributes are \emph{parameters} of the procedure of the nonterminal, synthesized attributes are its \emph{return values} \\
B. On-the-fly generation & recursive descent & the big ``code'' attribute is not built as a string; its pieces are \emph{emitted} (printed) as soon as they are known \\
C. Parser-stack records & table-driven LL (stack) & values are kept in \emph{records on the parser stack} and are copied from record to record \\ \bottomrule
\end{tabular}
\end{center}
A fourth way, for bottom-up parsers (marker nonterminals and attributes on the LR stack), belongs to the bottom-up parsing lectures; Section~\ref{sec:marker} shows the basic marker idea.

\subsubsection{Method A: recursive descent with arguments and return values}

\begin{defbox}{Recipe: one procedure per nonterminal}
For a nonterminal $A$ with inherited attributes $a_1,\dots$ and synthesized attributes $s_1,\dots$, write a procedure \texttt{A($a_1,\dots$)} that returns $s_1,\dots$. In its body, handle the chosen production from left to right:
\begin{enumerate}[nosep]
\item for a terminal: \texttt{match(token)} (and save its attribute, e.g.\ \texttt{lexval}, in a local variable if it is needed);
\item for a nonterminal $X$: compute its inherited attributes from the variables seen so far, \textbf{call} \texttt{X(\dots)}, and store the returned synthesized attributes in local variables;
\item for an action: write it as a statement at that point;
\item at the end: \texttt{return} the synthesized attributes of $A$.
\end{enumerate}
Because the SDD is L-attributed, every value an inherited attribute needs has already been computed when the call is made.
\end{defbox}

\begin{examplebox}{Example A1: the array type of \texttt{int [2][3]}}
The SDT of the previous subsection becomes three procedures. \texttt{C(b)} receives the inherited attribute $C.b$ as its argument and returns $C.t$:
\begin{lstlisting}
Type T() {
    Type b = B();              // B.t
    return C(b);               // C.b = B.t ;  T.t = C.t
}
Type B() {
    if (look == INT)  { match(INT);   return integer; }   // B.t
    else              { match(FLOAT); return float;   }
}
Type C(Type b) {               // b is the inherited attribute C.b
    if (look == '[') {
        match('[');  n = lexval;  match(NUM);  match(']');
        Type c1 = C(b);        // C1.b = C.b
        return array(n, c1);   // C.t = array(num.val, C1.t)
    }
    return b;                  // C -> epsilon:  C.t = C.b
}
\end{lstlisting}
Trace for \texttt{int [2][3]}: \texttt{T()} calls \texttt{B()} which returns \textit{integer}; then \texttt{C(integer)} reads \texttt{[2]} and calls \texttt{C(integer)}, which reads \texttt{[3]} and calls \texttt{C(integer)}; this call sees no \texttt{[}, so it returns \textit{integer}. The returns then build $\mathit{array}(3,\mathit{integer})$ and finally $\mathit{array}(2,\mathit{array}(3,\mathit{integer}))$. The values travel \emph{down} as arguments and \emph{up} as return values, exactly as in Figure~\ref{fig:typetree}.
\end{examplebox}

\begin{examplebox}{Example A2: sums and differences without left recursion}
For the SDT of Example~1 in Section~\ref{sec:leftrec}, the inherited attribute $R.i$ is the parameter of \texttt{R} and $R.s$ is its return value. The terminal \textbf{num} has the attribute \texttt{lexval}.
\begin{lstlisting}
int E() { int t = T();  return R(t); }       // R.i = T.val ;  E.val = R.s

int R(int i) {                               // i is R.i
    if (look == '+') { match('+'); int t = T(); return R(i + t); }
    if (look == '-') { match('-'); int t = T(); return R(i - t); }
    return i;                    // R -> epsilon:  R.s = R.i
    // R1.i = R.i +/- T.val  is the argument of the recursive call
}

int T() { int v = lexval;  match(NUM);  return v; }   // T.val = num.lexval
\end{lstlisting}
For \texttt{9-5+2}: \texttt{E()} gets $9$ from \texttt{T()} and calls \texttt{R(9)}; \texttt{R(9)} reads \texttt{-5} and calls \texttt{R(4)}; \texttt{R(4)} reads \texttt{+2} and calls \texttt{R(6)}; \texttt{R(6)} finds the end of the input and returns $6$, which every caller returns unchanged. The pointer-based variant for the syntax tree of Section~\ref{sec:lattr} has the same shape: \texttt{Node R(Node i)} returns \texttt{R(new Node('+', i, t))} instead of \texttt{R(i + t)}, and \texttt{return i} at the end.
\end{examplebox}

\begin{examplebox}{Example A3: code for a \texttt{while} statement}
The \textbf{while} statement of the Dragon Book (Chapter 5) is $S\to\mathbf{while}\,(\,C\,)\,S_1$. The attributes are: $S.next$ (inherited; the label after the statement), $C.true$ and $C.false$ (inherited; the jump targets of the condition), and the synthesized $S.code$ and $C.code$. The SDT creates two labels $L_1$ and $L_2$:
\begin{align*}
S \to \mathbf{while}\ \tok{(}\ &\{\ L_1=\mathit{new}();\ L_2=\mathit{new}();\ \at{C}{false}=\at{S}{next};\ \at{C}{true}=L_2\ \}\ C\ \tok{)}\\
&\{\ \at{S_1}{next}=L_1\ \}\ S_1\ \{\ \at{S}{code}=\mathit{label}\cc L_1\cc\at{C}{code}\cc\mathit{label}\cc L_2\cc\at{S_1}{code}\ \}
\end{align*}
The generated code is $L_1\!:\ C.code$ (it jumps to $L_2$ if the condition is true and to $S.next$ if false), then $L_2\!:\ S_1.code$, which ends with a jump back to $S_1.next=L_1$. (The flow-of-control SDD later in these notes, taken from Chapter~6 of the book, writes the same translation with an explicit \texttt{goto begin}.)

As a recursive-descent procedure, $S.next$ is the argument, $S.code$ the return value (a string), and the labels are local variables:
\begin{lstlisting}
string S(label next) {
    string Scode, Ccode;               // code strings
    label L1, L2;                      // local labels
    if (look == WHILE) {
        match(WHILE);  match('(');
        L1 = new();  L2 = new();
        Ccode = C(next, L2);           // C.false = S.next, C.true = L2
        match(')');
        Scode = S(L1);                 // S1.next = L1
        return "label" || L1 || Ccode || "label" || L2 || Scode;
    }
    else { /* other statement types */ }
}
\end{lstlisting}
Each call of \texttt{S} or \texttt{C} returns the code of its own part, and the caller concatenates the pieces in the order of the SDD.
\end{examplebox}

\subsubsection{Method B: on-the-fly code generation}
Method A builds the whole code of a statement as one long string and returns it, so the code of a big program is copied over and over as it is returned upward. We can avoid this when the main attribute (here $S.code$) is a \emph{concatenation of the pieces produced by its children, in the same order as the children appear in the body, with fixed strings between them}. Then, instead of building the string, each piece is simply \textbf{printed at the moment it is known}; the order of the printing is the order of the concatenation. The SDT of Example~A3 changes in just two places: the construction of $S.code$ disappears and two \textit{print} actions are added.
\begin{align*}
S \to \mathbf{while}\ \tok{(}\ &\{\ L_1=\mathit{new}();\ L_2=\mathit{new}();\ \at{C}{false}=\at{S}{next};\ \at{C}{true}=L_2;\ \mathit{print}(\text{``label''},L_1)\ \}\ C\ \tok{)}\\
&\{\ \at{S_1}{next}=L_1;\ \mathit{print}(\text{``label''},L_2)\ \}\ S_1
\end{align*}
\begin{lstlisting}
void S(label next) {                   // S.code is not returned: it is printed
    label L1, L2;
    if (look == WHILE) {
        match(WHILE);  match('(');
        L1 = new();  L2 = new();
        print("label", L1);            // the first piece of S.code
        C(next, L2);                   // C prints its own code
        match(')');
        print("label", L2);            // the next piece
        S(L1);                         // S1 prints its own code
    }
    else { /* other statement types */ }
}
\end{lstlisting}
The output is the same as before, but no code string is ever copied. This is the same idea as the incremental translation with \textit{gen} of Section~\ref{sec:exprtac}.

\begin{pitfallbox}{When on-the-fly generation is not possible}
Printing is correct only if the pieces appear in the code in the same order as the symbols in the production body. If a rule used $S.code=S_2.code\cc S_1.code$ (the code of the \emph{later} symbol first), the parser would reach $S_1$ first and print its code too early. In that case Method A, which returns strings, is needed.
\end{pitfallbox}

\subsubsection{Method C: attributes on the stack of a table-driven LL parser}
A table-driven LL parser has no procedures to hold local variables, so the attribute values are kept on its \textbf{stack} in extra records. The stack is drawn with its top at the \emph{left}; the next thing to be done is the leftmost entry. The rules below (the book calls them action records and synthesize records) are all we need:
\begin{enumerate}[nosep]
\item The \textbf{inherited attributes} of a nonterminal $A$ are stored in the stack entry of $A$.
\item Every \textbf{action} of the SDT becomes an \emph{action record} pushed at its position in the body. An action that computes an inherited attribute of $X$ stands immediately above $X$, so it can write into the entry of $X$.
\item Every nonterminal $X$ in a body gets a \textbf{synthesize record} $X_s$ pushed immediately \emph{below} $X$. The action at the end of $X$'s body stores the synthesized attribute of $X$ there.
\item \textbf{Copying.} An action record holds copies of the values it needs. They are copied into it at three moments: when the head of the production is expanded (its inherited attributes), when a terminal is matched (its \textit{lexval}), and when a synthesize record reaches the top of the stack (it is popped and its content is copied into the action record below it).
\item A record at the top of the stack is processed by executing the action and popping it.
\end{enumerate}

\begin{examplebox}{Example C1: the \texttt{while} statement on the LL stack}
Take the on-the-fly SDT of Method B, whose production is $S\to\mathbf{while}\ \tok{(}\ a_1\ C\ \tok{)}\ a_2\ S_1$, where $a_1$ is the first action (creates $L_1,L_2$, sets $C$'s attributes) and $a_2$ is the second (sets $S_1.next$). Let $S.next=x$, and let the new labels be $L_1=y$ and $L_2=z$. Only inherited attributes occur, so there are no synthesize records.
\begin{center}
\small
\begin{tabular}{@{}p{3.3cm} p{8.8cm} l@{}}
\toprule
\textbf{Moment} & \textbf{Stack (top at the left)} & \textbf{Output} \\ \midrule
Just before expanding $S$ & $S\,[next=x]\ \dots$ & \\
Immediately after expanding $S$ &
$\mathbf{while}\ \ \tok{(}\ \ [a_1:\ S.next=x,\ L_1,\ L_2]\ \ C\,[true,false]\ \ \tok{)}\ \ [a_2:\ L_1,\ L_2]\ \ S_1\,[next]\ \dots$ & \\
After \textbf{while}, \texttt{(} are matched and $a_1$ runs &
$C\,[true=z,\ false=x]\ \ \tok{)}\ \ [a_2:\ L_1=y,\ L_2=z]\ \ S_1\,[next]\ \dots$ & \texttt{label y} \\
After $C$ and \texttt{)} are processed and $a_2$ runs &
$S_1\,[next=y]\ \dots$ & \texttt{label z} \\ \bottomrule
\end{tabular}
\end{center}
Note the copying: when $S$ is expanded, the entry of $S$ disappears, so its inherited attribute $S.next=x$ is first \emph{copied} into the record of $a_1$. Action $a_1$ then creates $y$ and $z$, writes $C$'s attributes into the entry of $C$ directly below it, and copies $y$ and $z$ into the record of $a_2$, which will need them later.
\end{examplebox}

\begin{examplebox}{Example C2: synthesize records for \texttt{9-5+2}}
Use the SDT of Example~1 in Section~\ref{sec:leftrec}, with the actions named:
\begin{align*}
E &\to T\ \{a_1:\ R.i=T.val\}\ R\ \{a_2:\ E.val=R.s\}\\
R &\to +\ T\ \{b_1:\ R_1.i=R.i+T.val\}\ R_1\ \{b_2:\ R.s=R_1.s\}\\
  &\mid\ -\ T\ \{b_1:\ R_1.i=R.i-T.val\}\ R_1\ \{b_2:\ R.s=R_1.s\}\ \mid\ \varepsilon\ \{c:\ R.s=R.i\}\\
T &\to \mathbf{num}\ \{d:\ T.val=\mathbf{num}.lexval\}
\end{align*}
\begin{center}
\small
\begin{tabular}{@{}p{4.2cm} p{7.8cm} l@{}}
\toprule
\textbf{Moment} & \textbf{Stack (top at the left)} & \textbf{Input} \\ \midrule
Start & $E\ E_s$ & \texttt{9-5+2} \\
$E$ expanded & $T\ T_s\ a_1\ R\ R_s\ a_2\ E_s$ & \texttt{9-5+2} \\
$T$ done ($T_s{=}9$ copied into $a_1$), $a_1$ run & $R[i{=}9]\ R_s\ a_2\ E_s$ & \texttt{-5+2} \\
$R$ expanded by $-$ ($R.i=9$ copied into $b_1$) & $-\ T\ T_s\ [b_1:\ R.i{=}9]\ R\ R_s\ b_2\ R_s\ a_2\ E_s$ & \texttt{-5+2} \\
$T$ done ($T.val=5$), $b_1$ run: $R_1.i=9-5=4$ & $R[i{=}4]\ R_s\ b_2\ R_s\ a_2\ E_s$ & \texttt{+2} \\
second $R$ expanded by $+$, $b_1$ run: $R_1.i=4+2=6$ & $R[i{=}6]\ R_s\ b_2\ R_s\ b_2\ R_s\ a_2\ E_s$ & end \\
$R\to\varepsilon$, action $c$: $R.s=R.i$ & $R_s{=}6\ b_2\ R_s\ b_2\ R_s\ a_2\ E_s$ & end \\
each $b_2$ copies $R_1.s$ into its $R_s$, then $a_2$ & $E_s{=}6$ & end \\ \bottomrule
\end{tabular}
\end{center}
The inherited value $R.i$ moves \emph{right} through the action records ($9\to4\to6$), and the final $6$ moves \emph{left} through the synthesize records, one for each $R$, until it reaches $E_s$.
\end{examplebox}

\begin{notebox}{Which method to use?}
Method A is the easiest to write and to read, and it handles any L-attributed SDD; the price is the strings that are returned. Method B is Method A without the strings and is the choice for code generation. Method C is what a generated, table-driven LL parser does; it is rarely written by hand. All three execute the same SDT, and all three need an L-attributed SDD: an inherited attribute that depends on a symbol to its right could not be evaluated, because that symbol has not been parsed yet.
\end{notebox}

\subsection{SDD for three-address code}
\label{sec:exprtac}
We use the following:
\begin{itemize}
\item \at{E}{addr}: the address (name, constant, or temporary) that holds the value of $E$.
\item \at{E}{code} (or \at{S}{code}): the three-address instructions that evaluate $E$ (or execute $S$).
\item $\mathit{newTemp}()$ (written \textbf{new} \textit{Temp}): returns a fresh temporary $t_1, t_2,\dots$ in successive calls.
\item $\gen{\cdots}$: builds a three-address instruction. $\cc$ denotes concatenation of instruction sequences.
\end{itemize}

\begin{table}[htbp]
\centering
\small
\begin{tabular}{@{}L{3.3cm} L{11.4cm}@{}}
\toprule
\textbf{Production} & \textbf{Semantic rules} \\ \midrule
$S \to \mathbf{id} = E\ ;$ &
$\at{S}{code} = \at{E}{code} \cc \gen{\mathit{top}.\mathit{get}(\at{\mathbf{id}}{lexeme})\ \tok{=}\ \at{E}{addr}}$ \\
$E \to E_1 + E_2$ &
$\at{E}{addr} = \mathbf{new}\ \mathit{Temp}()$\\ &
$\at{E}{code} = \at{E_1}{code} \cc \at{E_2}{code} \cc \gen{\at{E}{addr}\ \tok{=}\ \at{E_1}{addr}\ \tok{+}\ \at{E_2}{addr}}$ \\
$E \to E_1 * E_2$ &
$\at{E}{addr} = \mathbf{new}\ \mathit{Temp}()$\\ &
$\at{E}{code} = \at{E_1}{code} \cc \at{E_2}{code} \cc \gen{\at{E}{addr}\ \tok{=}\ \at{E_1}{addr}\ \tok{*}\ \at{E_2}{addr}}$ \\
$E \to -\,E_1$ &
$\at{E}{addr} = \mathbf{new}\ \mathit{Temp}()$\\ &
$\at{E}{code} = \at{E_1}{code} \cc \gen{\at{E}{addr}\ \tok{=}\ \tok{minus}\ \at{E_1}{addr}}$ \\
$E \to (\,E_1\,)$ &
$\at{E}{addr} = \at{E_1}{addr}$;\quad $\at{E}{code} = \at{E_1}{code}$ \\
$E \to \mathbf{id}$ &
$\at{E}{addr} = \mathit{top}.\mathit{get}(\at{\mathbf{id}}{lexeme})$;\quad $\at{E}{code} = \tok{''}$ \\ \bottomrule
\end{tabular}
\caption{SDD to produce three-address code for expressions and assignments (Dragon Book Fig.~6.19).}
\label{tab:expr-sdd}
\end{table}

\begin{notebox}{Remark}
Here $\mathit{top}$ is the current symbol table; $\mathit{top}.\mathit{get}(\textit{name})$ returns the symbol-table entry. The code of a node is the \emph{concatenation} of its children's code followed by one new instruction, so the instructions are produced in postfix (evaluation) order. The $\at{}{code}$ attribute is a long string, so this SDD is inefficient in practice, which motivates the incremental approach below.
\end{notebox}

The grammar $E\to E_1+E_2\mid E_1*E_2\mid-E_1\mid(E_1)\mid\mathbf{id}$ is ambiguous. Precedence ($-$ highest, then $*$, then $+$) and left-associativity are supplied either by parser-generator declarations or by rewriting the grammar with levels $E, T, F$. This does not change the semantic rules: they are written once per \emph{operator}, whatever the grammar levels are called. The $*$ rule is the $+$ rule with the operator replaced; the rule for binary $-$ and for $/$ is identical again.

\subsection{Incremental translation (SDT with \texttt{gen} emitting directly)}
Building \at{E}{code} as a string copies code repeatedly. In an \emph{incremental} scheme, $\mathit{gen}()$ \textbf{appends} the instruction to an output stream/array as soon as the action is executed. The code attribute is not stored. Since actions run in the correct order (postfix), the instructions come out in the right order.

\begin{table}[htbp]
\centering

\subsection{Addressing array elements}
Let an array be stored in a contiguous block of memory with base address $\mathit{base}$ and element width $w$.

\paragraph{One-dimensional array} $A[\mathit{low}\ \dots\ \mathit{high}]$:
\[
\text{address of } A[i] \;=\; \mathit{base} + (i - \mathit{low}) \times w
\]
If $\mathit{low}=0$ this is simply $\mathit{base} + i \times w$.

\paragraph{Two-dimensional array} (row-major) $A[n_1][n_2]$ with element width $w$:
\[
\text{address of } A[i_1][i_2] \;=\; \mathit{base} + (i_1 \times n_2 + i_2) \times w
\]
\paragraph{$k$ dimensions} $A[n_1]\cdots[n_k]$ (row-major, 0-based):
\[
\mathit{base} + \bigl( (\cdots((i_1 n_2 + i_2) n_3 + i_3) \cdots ) n_k + i_k \bigr)\times w
\]
Equivalently, using the \emph{widths of sub-arrays} $w_1 = n_2 \cdots n_k \cdot w,\ w_2 = n_3\cdots n_k \cdot w, \dots,\ w_k = w$:
\[
\mathit{base} + i_1 \times w_1 + i_2 \times w_2 + \cdots + i_k \times w_k.
\]
This form is the one used in the translation scheme.

\subsection{Translation of array references}
Grammar (with nonterminal $L$ for an array location):
\begin{align*}
S &\to \mathbf{id} = E\ ;\ \mid\ L = E\ ;\\
E &\to E_1 + E_2\ \mid\ \mathbf{id}\ \mid\ L\\
L &\to \mathbf{id}\,[\,E\,]\ \mid\ L_1\,[\,E\,]
\end{align*}
Attributes of $L$: \at{L}{array} (symbol-table entry of the array), \at{L}{type} (type of the \emph{sub-array} generated by $L$), \at{L}{addr} (a temporary accumulating the \emph{offset}).

\begin{table}[htbp]
\centering
\small
\begin{tabular}{@{}L{2.4cm} L{12.2cm}@{}}
\toprule
\textbf{Production} & \textbf{Semantic action} \\ \midrule
$S \to \mathbf{id}=E\ ;$ & $\{\ \mathit{gen}(\mathit{top}.\mathit{get}(\at{\mathbf{id}}{lexeme})\ \tok{=}\ \at{E}{addr});\ \}$ \\[2pt]
$S \to L=E\ ;$ & $\{\ \mathit{gen}(\at{L}{array}.\mathit{base}\ \tok{[}\ \at{L}{addr}\ \tok{]}\ \tok{=}\ \at{E}{addr});\ \}$ \\[2pt]
$E \to E_1+E_2$ & $\{\ \at{E}{addr}=\mathbf{new}\ \mathit{Temp}();\ \mathit{gen}(\at{E}{addr}\ \tok{=}\ \at{E_1}{addr}\ \tok{+}\ \at{E_2}{addr});\ \}$ \\[2pt]
$E \to \mathbf{id}$ & $\{\ \at{E}{addr}=\mathit{top}.\mathit{get}(\at{\mathbf{id}}{lexeme});\ \}$ \\[2pt]
$E \to L$ & $\{\ \at{E}{addr}=\mathbf{new}\ \mathit{Temp}();\ \mathit{gen}(\at{E}{addr}\ \tok{=}\ \at{L}{array}.\mathit{base}\ \tok{[}\ \at{L}{addr}\ \tok{]});\ \}$ \\[2pt]
$L \to \mathbf{id}\,[\,E\,]$ & $\{\ \at{L}{array}=\mathit{top}.\mathit{get}(\at{\mathbf{id}}{lexeme});\ \at{L}{type}=\at{L}{array}.\mathit{type}.\mathit{elem};$\\
 & $\ \ \at{L}{addr}=\mathbf{new}\ \mathit{Temp}();\ \mathit{gen}(\at{L}{addr}\ \tok{=}\ \at{E}{addr}\ \tok{*}\ \at{L}{type}.\mathit{width});\ \}$ \\[2pt]
$L \to L_1\,[\,E\,]$ & $\{\ \at{L}{array}=\at{L_1}{array};\ \at{L}{type}=\at{L_1}{type}.\mathit{elem};$\\
 & $\ \ t=\mathbf{new}\ \mathit{Temp}();\ \at{L}{addr}=\mathbf{new}\ \mathit{Temp}();$\\
 & $\ \ \mathit{gen}(t\ \tok{=}\ \at{E}{addr}\ \tok{*}\ \at{L}{type}.\mathit{width});\ \mathit{gen}(\at{L}{addr}\ \tok{=}\ \at{L_1}{addr}\ \tok{+}\ t);\ \}$ \\ \bottomrule
\end{tabular}
\caption{Semantic actions for array references (Dragon Book Fig.~6.22).}
\end{table}

\begin{examplebox}{Worked example: $c + a[i][j]$ where \texttt{a} is \texttt{int a[2][3]}}
Types: \at{a}{type} $= \mathit{array}(2,\ \mathit{array}(3,\ \mathit{integer}))$, so the width of one row is $3\times 4 = 12$ and of an element is $4$.

\begin{enumerate}[nosep]
\item $L \to \mathbf{id}[E]$ with $E = i$: $\at{L}{type}=\mathit{array}(3,\mathit{integer})$, width 12 \;$\Rightarrow$\; \texttt{t1 = i * 12}.
\item $L \to L_1[E]$ with $E = j$: $\at{L}{type}=\mathit{integer}$, width 4 \;$\Rightarrow$\; \texttt{t2 = j * 4}, \texttt{t3 = t1 + t2}.
\item $E \to L$: \texttt{t4 = a[t3]}.
\item $E \to E_1 + E_2$: \texttt{t5 = c + t4}.
\end{enumerate}
\begin{lstlisting}
t1 = i * 12
t2 = j * 4
t3 = t1 + t2
t4 = a[t3]
t5 = c + t4
\end{lstlisting}

And for the assignment $x = a[i][j]$ the code is the first four instructions followed by \texttt{x = t4}.
\end{examplebox}

\begin{examplebox}{Worked example: a three-dimensional array and a store}
Let \texttt{int a[2][3][4]} (so $w=4$). The widths of the sub-arrays are $w_3=4$ (one element), $w_2=4\cdot4=16$ (one innermost row of 4 elements) and $w_1=3\cdot4\cdot4=48$ (one $3\times4$ plane); the whole array occupies $2\cdot48=96$ bytes. The statement \texttt{x = a[i][j][k];} becomes
\begin{lstlisting}
t1 = i * 48
t2 = j * 16
t3 = t1 + t2
t4 = k * 4
t5 = t3 + t4
t6 = a[t5]
x  = t6
\end{lstlisting}
Each extra subscript adds exactly two instructions (a multiplication and an addition), as in the rule for $L\to L_1[E]$. For a \emph{store}, \texttt{a[i][j] = x;} with \texttt{int a[2][3]} uses the rule $S\to L=E\,;$, which ends with an indexed assignment instead of an indexed load:
\begin{lstlisting}
t1 = i * 12
t2 = j * 4
t3 = t1 + t2
a[t3] = x
\end{lstlisting}
\end{examplebox}

\begin{pitfallbox}{Index versus offset}
In \texttt{t4 = a[t3]} the value in \texttt{t3} is a \emph{byte offset} from the base of \texttt{a}, not an element index as in the C source. That is why every subscript is multiplied by the width of the thing it selects. (In the book's three-address code, \texttt{x = y[i]} means ``the value at the memory location $i$ units beyond $y$''.)
\end{pitfallbox}

\section{Type Checking and Type Conversion}
%====================================================================

\paragraph{Type expressions} represent the type of a language construct: basic types (\texttt{int}, \texttt{float}, \texttt{char}, \texttt{boolean}, \texttt{void}), \textit{array}$(n, T)$, \textit{record}, pointer, and function types $s \to t$.

\paragraph{Type checking} comes in two forms: \textbf{synthesis} (the type of an expression is built from the types of its sub-expressions, e.g., for $E_1 + E_2$) and \textbf{inference} (the type of a construct is determined from the way it is used).

\begin{examplebox}{Example: three static checks}
Static checking attaches a rule to a production and reports an error when the rule fails. With \texttt{int a[10]; int n; float f;}:
\begin{center}
\small
\begin{tabular}{@{}l L{5.6cm} L{4.6cm}@{}}
\toprule
\textbf{Source} & \textbf{Rule that fails} & \textbf{Message} \\ \midrule
\texttt{x = a[2.5];} & in $L\to\mathbf{id}[E]$ the index $E$ must have type \texttt{int} & array index must be an integer \\
\texttt{y = a + n;} & $+$ is defined for numeric types only; $a$ has type $\mathit{array}(10,\texttt{int})$ & operand of $+$ is not a number \\
\texttt{if (f) x = 1;} & the condition in \texttt{if (}$E$\texttt{)} must have type \texttt{boolean} & \texttt{float} used as condition (C would accept it and test $f\ne0$) \\ \bottomrule
\end{tabular}
\end{center}
Each check is just one more semantic rule: it computes nothing, it only compares attribute values and calls an error routine, which is another example of a rule with a side effect.
\end{examplebox}

\subsection{Type conversion (coercion)}
For $E \to E_1 + E_2$ where operand types may differ (e.g., \texttt{int} and \texttt{float}), the compiler inserts conversions. Conversions that cannot lose information in principle (\emph{widening}) may be inserted by the compiler automatically (\emph{coercion}); the reverse direction (\emph{narrowing}) needs an explicit cast written by the programmer. Figure~\ref{fig:typehier} shows the usual hierarchy. In these notes we use only \texttt{int} $<$ \texttt{float}.

For $E \to E_1 + E_2$ (and likewise for $-$, $*$, $/$) the result has the \emph{wider} of the two operand types,
\[
\at{E}{type} = \max(\at{E_1}{type},\ \at{E_2}{type}),
\]
and the helper $\mathit{widen}(a, t, w)$ converts address $a$ of type $t$ to type $w$:

\begin{lstlisting}
Addr widen(Addr a, Type t, Type w) {
    if (t == w) return a;
    else if (t == integer && w == float) {
        temp = new Temp();
        gen(temp '=' '(float)' a);
        return temp;
    }
    else error;
}
\end{lstlisting}

\begin{center}
\small
\begin{tabular}{@{}L{3.1cm} L{11.4cm}@{}}
\toprule
\textbf{Production} & \textbf{Semantic action} \\ \midrule
$E \to E_1 + E_2$ &
$\{\ \at{E}{type}=\max(\at{E_1}{type},\at{E_2}{type});$\\
& $\ \ a_1=\mathit{widen}(\at{E_1}{addr},\at{E_1}{type},\at{E}{type});$\\
& $\ \ a_2=\mathit{widen}(\at{E_2}{addr},\at{E_2}{type},\at{E}{type});$\\
& $\ \ \at{E}{addr}=\mathbf{new}\ \mathit{Temp}();\ \mathit{gen}(\at{E}{addr}\ \tok{=}\ a_1\ \tok{+}\ a_2);\ \}$ \\ \bottomrule
\end{tabular}
\end{center}

\begin{examplebox}{Example}
Let \texttt{x} be \texttt{float}, and \texttt{i, j} be \texttt{int}. For $x = i * j + x$ we get:
\begin{lstlisting}
t1 = i * j          // int * int -> int
t2 = (float) t1     // widen to float
t3 = t2 + x         // float + float
x  = t3
\end{lstlisting}
\end{examplebox}

\begin{examplebox}{Worked example: widening on \emph{both} sides, $x = i + j * x$}
Let \texttt{x} be \texttt{float} and \texttt{i, j} be \texttt{int}. The code is emitted at reductions, so the product $j*x$ (reduced first) comes before the sum:
\begin{enumerate}[nosep]
\item $E\to E_1*E_2$ with $E_1=j$ (\texttt{int}) and $E_2=x$ (\texttt{float}): $E.type=\texttt{float}$; $\mathit{widen}(j)$ emits \texttt{t1 = (float) j}; $\mathit{widen}(x)$ does nothing; then \texttt{t2 = t1 * x}.
\item $E\to E_1+E_2$ with $E_1=i$ (\texttt{int}) and $E_2$ of type \texttt{float}: $\mathit{widen}(i)$ emits \texttt{t3 = (float) i}; then \texttt{t4 = t3 + t2}.
\item $S\to\mathbf{id}=E\,;$ emits \texttt{x = t4}.
\end{enumerate}
\begin{lstlisting}
t1 = (float) j
t2 = t1 * x
t3 = (float) i
t4 = t3 + t2
x  = t4
\end{lstlisting}
Note that $i$, which is written first, is converted \emph{after} $j$: the order of the instructions follows the order of the reductions, not the order of the source text.
\end{examplebox}

\section{Control Flow: Boolean Expressions and Statements}
%====================================================================

In programming languages, boolean expressions are used for two purposes:
\begin{enumerate}[nosep]
\item to \textbf{compute logical values} (e.g., \texttt{flag = a < b \&\& c;}), and
\item as \textbf{conditional expressions} in \texttt{if}, \texttt{while}, and \texttt{for} (flow-of-control).
\end{enumerate}
We use the grammar
\[
B \to B \,|\!|\, B \ \mid\ B\ \&\&\ B\ \mid\ !\,B\ \mid\ (B)\ \mid\ E\ \mathit{rel}\ E\ \mid\ \mathbf{true}\ \mid\ \mathbf{false}
\]
with $|\!|$ standing for the C operator \texttt{||}; \texttt{||} and \texttt{\&\&} are left-associative, \texttt{||} has lower precedence than \texttt{\&\&}, which is lower than \texttt{!}.

\subsection{Short-circuit (jumping) code}
In \textbf{short-circuit code}, the operators \texttt{\&\&}, \texttt{||} and \texttt{!} do not appear in the generated code. Instead a boolean expression is translated into jumps to labels: control \emph{reaches} one position if the expression is true and another if it is false. In
\[
\texttt{if (x < 100 || x > 200 \&\& x != y) x = 0;}
\]
the first test \texttt{x<100} being true makes the other tests unnecessary. The generated code is:

\begin{lstlisting}
        if x < 100 goto L2
        goto L3
L3:     if x > 200 goto L4
        goto L1
L4:     if x != y goto L2
        goto L1
L2:     x = 0
L1:     ...
\end{lstlisting}
(Compare with \emph{value} code, which would compute 0/1 into temporaries and use \texttt{\&\&} and \texttt{||} at run time.)

\begin{pitfallbox}{Short-circuit evaluation is a semantic guarantee, not only an optimisation}
In \texttt{if (p != NULL \&\& p->x > 0) \dots} the second operand must \emph{not} be evaluated when $p$ is null, otherwise the program dereferences a null pointer. Jumping code gives this behaviour for free: the test of \texttt{p->x} is only reached through the \emph{true} exit of \texttt{p != NULL}. Value code that first computes both operands would crash.
\end{pitfallbox}

\paragraph{Boolean values in assignments.} A boolean expression is also used to compute a \emph{value}, e.g.\ \texttt{flag = a < b \&\& c;}. The jumping code is reused, and the two exits set the variable:
\begin{lstlisting}
        if a < b goto L1
        goto L3
L1:     if c goto L2
        goto L3
L2:     flag = true
        goto L4
L3:     flag = false
L4:
\end{lstlisting}

\subsection{Flow-of-control statements: SDD with inherited labels}
Grammar for statements:
\[
P \to S, \qquad S \to \mathbf{assign}\ \mid\ \mathbf{if}\,(B)\,S_1\ \mid\ \mathbf{if}\,(B)\,S_1\ \mathbf{else}\ S_2\ \mid\ \mathbf{while}\,(B)\,S_1\ \mid\ S_1\,S_2
\]
\textbf{Inherited attributes} (labels):
\begin{itemize}
\item \at{B}{true}: the label to jump to if $B$ is true; \at{B}{false}: the label if $B$ is false.
\item \at{S}{next}: the label of the instruction that follows the code for $S$.
\end{itemize}
\textbf{Synthesized attribute}: \at{S}{code}, \at{B}{code}. The function $\mathit{newlabel}()$ creates a fresh label $L_1, L_2, \dots$, and $\lbl{L}$ attaches label $L$ to the next instruction.

\begin{notebox}{How to remember the \texttt{||} and \texttt{\&\&} rules}
\begin{itemize}[nosep]
\item $B_1 \,||\, B_2$: if $B_1$ is true we are done (go to \textit{B.true}); if false, \emph{test $B_2$}, so $B_1.\mathit{false}$ is a new label placed in front of $B_2.\mathit{code}$.
\item $B_1 \,\&\&\, B_2$: if $B_1$ is false we are done (go to \textit{B.false}); if true, \emph{test $B_2$}, so $B_1.\mathit{true}$ is a new label in front of $B_2.\mathit{code}$.
\item $!\,B_1$: simply \emph{swap} the true and false labels.
\end{itemize}
\end{notebox}

\begin{examplebox}{Worked example: \texttt{if (x < 100 || x > 200 \&\& x != y) x = 0;}}
\textbf{Step 1.} $P \to S$: \at{S}{next} $= L_1$.

\textbf{Step 2.} $S \to \mathbf{if}(B)S_1$: \at{B}{true} $= L_2$, \at{B}{false} $= L_1$, \at{S_1}{next} $= L_1$.

\textbf{Step 3.} $B = B_1 \,||\, B_2$, where $B_1 \equiv x<100$ and $B_2 \equiv (x>200 \;\&\&\; x\ne y)$:
\begin{itemize}[nosep]
\item $B_1$: true $= L_2$, false $= L_3$ (new).
\item $B_2$: true $= L_2$, false $= L_1$.
\end{itemize}
\textbf{Step 4.} $B_2 = B_3 \,\&\&\, B_4$ with $B_3 \equiv x>200$, $B_4 \equiv x \ne y$:
\begin{itemize}[nosep]
\item $B_3$: true $= L_4$ (new), false $= L_1$.
\item $B_4$: true $= L_2$, false $= L_1$.
\end{itemize}
\textbf{Step 5.} Assemble: $B_1.code \cc L_3{:}\ B_2.code$, with $B_2.code = B_3.code \cc L_4{:}\ B_4.code$, followed by $L_2{:}\ S_1.code$ and finally $L_1{:}$

\begin{lstlisting}
        if x < 100 goto L2
        goto L3
L3:     if x > 200 goto L4
        goto L1
L4:     if x != y goto L2
        goto L1
L2:     x = 0
L1:
\end{lstlisting}
Observe the redundant jumps (\texttt{goto L3} immediately followed by \texttt{L3:}) -- a later optimisation phase or the \emph{backpatching} method with fall-through can remove them.
\end{examplebox}

\begin{examplebox}{Worked example: \texttt{while (a < b) \{ if (c < d) x = y + z; \}}}
\begin{lstlisting}
L1:     if a < b goto L2        // begin / B.code
        goto L0                 // B.false = S.next
L2:     if c < d goto L3        // inner if: B.true = L3
        goto L1                 // inner S.next = begin = L1
L3:     t1 = y + z
        x = t1
        goto L1                 // goto begin
L0:                             // S.next
\end{lstlisting}
\end{examplebox}

\subsection{Avoiding redundant gotos (fall-through)}
Instead of
\begin{lstlisting}
        if x > 200 goto L4
        goto L1
L4:     ...
\end{lstlisting}
we can generate the shorter form \texttt{ifFalse x > 200 goto L1} followed by the code at \texttt{L4}: if the true label is the next instruction (denote it by the special label \textit{fall}), only one jump is needed. The rule for $B \to E_1\ \mathit{rel}\ E_2$ becomes: let $\mathit{test} = E_1.addr\ rel.op\ E_2.addr$:
\begin{center}
\small
\begin{tabular}{@{}l l@{}}
\toprule
\textbf{Condition} & \textbf{Generated jump code} \\ \midrule
\at{B}{true}\ $\ne$ \textit{fall} and \at{B}{false}\ $\ne$ \textit{fall} & \texttt{if test goto B.true} \quad \texttt{goto B.false} \\
\at{B}{true}\ $\ne$ \textit{fall} and \at{B}{false} = \textit{fall} & \texttt{if test goto B.true} \\
\at{B}{true} = \textit{fall} and \at{B}{false}\ $\ne$ \textit{fall} & \texttt{ifFalse test goto B.false} \\
both = \textit{fall} & (no instruction) \\ \bottomrule
\end{tabular}
\end{center}

\paragraph{The statement and operator rules change too.} Let \textit{fall} mean ``the next instruction in sequence''. The new rules (Dragon Book Section 6.6.5) are:
\begin{center}
\small
\begin{tabular}{@{}L{2.9cm} L{11.7cm}@{}}
\toprule
\textbf{Production} & \textbf{Semantic rules} \\ \midrule
$S\to\mathbf{if}\,(B)\,S_1$ & $\at{B}{true}=\textit{fall}$;\ \ $\at{B}{false}=\at{S_1}{next}=\at{S}{next}$;\ \ $\at{S}{code}=\at{B}{code}\cc\at{S_1}{code}$ \\[3pt]
$B\to B_1\,|\!|\,B_2$ &
$\at{B_1}{true}=$ (\at{B}{true} if $\ne$ \textit{fall}, else a new label);\ \ $\at{B_1}{false}=\textit{fall}$;\ \ $\at{B_2}{true}=\at{B}{true}$;\ \ $\at{B_2}{false}=\at{B}{false}$\\
& $\at{B}{code}=\at{B_1}{code}\cc\at{B_2}{code}$ if $\at{B}{true}\ne\textit{fall}$; otherwise $\at{B_1}{code}\cc\at{B_2}{code}\cc\lbl{\at{B_1}{true}}$ \\[3pt]
$B\to B_1\ \&\&\ B_2$ &
$\at{B_1}{true}=\textit{fall}$;\ \ $\at{B_1}{false}=$ (\at{B}{false} if $\ne$ \textit{fall}, else a new label);\ \ $\at{B_2}{true}=\at{B}{true}$;\ \ $\at{B_2}{false}=\at{B}{false}$\\
& $\at{B}{code}=\at{B_1}{code}\cc\at{B_2}{code}$ if $\at{B}{false}\ne\textit{fall}$; otherwise $\at{B_1}{code}\cc\at{B_2}{code}\cc\lbl{\at{B_1}{false}}$ \\ \bottomrule
\end{tabular}
\end{center}
The extra label in the ``otherwise'' case is needed because when $B_1$ is decisive the control must jump \emph{past} $B_2$, to the end of $B.code$.

\begin{examplebox}{Worked example: the same statement with fall-through}
For \texttt{if (x < 100 || x > 200 \&\& x != y) x = 0;} start with $B.true=\textit{fall}$ and $B.false=L_1$. For $B_1\,||\,B_2$: since $B.true=\textit{fall}$, $B_1.true=L_2$ (new) and $B_1.false=\textit{fall}$; $B_2$ inherits $B.true=\textit{fall}$ and $B.false=L_1$. For $B_2=B_3\,\&\&\,B_4$: $B_3.true=B_4.true=\textit{fall}$ and $B_3.false=B_4.false=L_1$. The relational rule then gives
\begin{lstlisting}
        if x < 100 goto L2
        ifFalse x > 200 goto L1
        ifFalse x != y goto L1
L2:     x = 0
L1:
\end{lstlisting}
Only 4 instructions (3 tests and the assignment) instead of 7, and no useless \texttt{goto}s.
\end{examplebox}

\section{Backpatching}
\label{sec:backpatch}
%====================================================================

\subsection{The problem and the idea}
In the one-pass, label-based scheme above we needed \emph{inherited} labels (\at{B}{true}, \at{S}{next}) because a jump may be generated \emph{before} its target is known. Inherited attributes make one-pass \textbf{bottom-up} translation awkward. \textbf{Backpatching} avoids this:
\begin{itemize}
\item When a jump is generated, its \emph{target is left blank}.
\item Each such incomplete jump is put on a \textbf{list} of jumps that will eventually go to the same target.
\item When the target address becomes known, the instructions on the list are \emph{patched} (filled in).
\end{itemize}
Thus we only need \emph{synthesized} attributes (lists of instruction indices), and the whole translation can be done in a single bottom-up pass.

\begin{defbox}{Backpatching primitives}
\begin{itemize}
\item $\mathit{makelist}(i)$: create a new list containing only $i$, an index into the instruction array; return a pointer to it.
\item $\mathit{merge}(p_1, p_2)$: concatenate the lists pointed to by $p_1$ and $p_2$; return the merged list.
\item $\mathit{backpatch}(p, i)$: insert $i$ as the target label for each instruction on the list $p$.
\item $\mathit{nextinstr}$: global variable containing the index of the next instruction to be generated. $\mathit{emit}(\dots)$ appends an instruction and increments it.
\end{itemize}
\end{defbox}

\subsection{Boolean expressions}
Synthesized attributes: \at{B}{truelist} (instructions that jump when $B$ is true) and \at{B}{falselist} (when false). A \textbf{marker nonterminal} $M \to \varepsilon$ records the index of the next instruction (\at{M}{instr}).

\begin{table}[htbp]
\centering
\small
\begin{tabular}{@{}L{3.3cm} L{11.3cm}@{}}
\toprule
\textbf{Production} & \textbf{Semantic action} \\ \midrule
$B \to B_1 \,|\!|\, M\ B_2$ &
$\{\ \mathit{backpatch}(\at{B_1}{falselist},\ \at{M}{instr});$\\
& $\ \ \at{B}{truelist}=\mathit{merge}(\at{B_1}{truelist},\ \at{B_2}{truelist});\ \ \at{B}{falselist}=\at{B_2}{falselist};\ \}$ \\[3pt]
$B \to B_1\ \&\&\ M\ B_2$ &
$\{\ \mathit{backpatch}(\at{B_1}{truelist},\ \at{M}{instr});$\\
& $\ \ \at{B}{truelist}=\at{B_2}{truelist};\ \ \at{B}{falselist}=\mathit{merge}(\at{B_1}{falselist},\ \at{B_2}{falselist});\ \}$ \\[3pt]
$B \to !\,B_1$ &
$\{\ \at{B}{truelist}=\at{B_1}{falselist};\ \at{B}{falselist}=\at{B_1}{truelist};\ \}$ \\[3pt]
$B \to (\,B_1\,)$ &
$\{\ \at{B}{truelist}=\at{B_1}{truelist};\ \at{B}{falselist}=\at{B_1}{falselist};\ \}$ \\[3pt]
$B \to E_1\ \mathit{rel}\ E_2$ &
$\{\ \at{B}{truelist}=\mathit{makelist}(\mathit{nextinstr});\ \at{B}{falselist}=\mathit{makelist}(\mathit{nextinstr}+1);$\\
& $\ \ \mathit{emit}(\tok{if}\ \at{E_1}{addr}\ \mathit{rel.op}\ \at{E_2}{addr}\ \tok{goto}\ \_);\ \ \mathit{emit}(\tok{goto}\ \_);\ \}$ \\[3pt]
$B \to \mathbf{true}$ &
$\{\ \at{B}{truelist}=\mathit{makelist}(\mathit{nextinstr});\ \mathit{emit}(\tok{goto}\ \_);\ \}$ \\[3pt]
$B \to \mathbf{false}$ &
$\{\ \at{B}{falselist}=\mathit{makelist}(\mathit{nextinstr});\ \mathit{emit}(\tok{goto}\ \_);\ \}$ \\[3pt]
$M \to \varepsilon$ &
$\{\ \at{M}{instr}=\mathit{nextinstr};\ \}$ \\ \bottomrule
\end{tabular}
\caption{Translation scheme for boolean expressions using backpatching (Dragon Book Fig.~6.43).}
\end{table}

\begin{examplebox}{Worked example: $x < 100 \;||\; x > 200 \;\&\&\; x \ne y$ (instructions start at index 100)}
\textbf{Parse structure:} $B \Rightarrow B_1 \,||\, M_1\, B_2$, where $B_2 \Rightarrow B_3 \,\&\&\, M_2\, B_4$.

\begin{enumerate}[nosep]
\item $B_1 \equiv x<100$: emit \texttt{100: if x<100 goto \_}, \texttt{101: goto \_}\\
 \hspace*{1em} $B_1.truelist=\{100\}$, $B_1.falselist=\{101\}$.
\item $M_1.instr = 102$.
\item $B_3 \equiv x>200$: emit \texttt{102: if x>200 goto \_}, \texttt{103: goto \_}\\
 \hspace*{1em} $B_3.truelist=\{102\}$, $B_3.falselist=\{103\}$.
\item $M_2.instr = 104$.
\item $B_4 \equiv x\ne y$: emit \texttt{104: if x!=y goto \_}, \texttt{105: goto \_}\\
 \hspace*{1em} $B_4.truelist=\{104\}$, $B_4.falselist=\{105\}$.
\item Reduce $B_2 \to B_3 \,\&\&\, M_2\, B_4$:\ \ $\mathit{backpatch}(\{102\},104)$ $\Rightarrow$ instruction 102 becomes \texttt{if x>200 goto 104}.\\
 \hspace*{1em} $B_2.truelist=\{104\}$, $B_2.falselist=\mathit{merge}(\{103\},\{105\})=\{103,105\}$.
\item Reduce $B \to B_1 \,||\, M_1\, B_2$:\ \ $\mathit{backpatch}(\{101\},102)$ $\Rightarrow$ instruction 101 becomes \texttt{goto 102}.\\
 \hspace*{1em} $B.truelist=\mathit{merge}(\{100\},\{104\})=\{100,104\}$, $B.falselist=\{103,105\}$.
\end{enumerate}
\textbf{Result} (still incomplete -- the lists will be patched by the enclosing statement):
\begin{lstlisting}
100:  if x < 100 goto _      <- on truelist
101:  goto 102
102:  if x > 200 goto 104

\subsection{Flow-of-control statements}
Synthesized attribute \at{S}{nextlist}: list of jumps to the instruction that follows $S$. We use markers $M \to \varepsilon$ (records \textit{nextinstr}) and $N \to \varepsilon$ (emits an incomplete \texttt{goto} and returns it on a list).

Grammar:
\begin{align*}
S &\to \mathbf{if}\,(B)\,S_1 \mid \mathbf{if}\,(B)\,S_1\ \mathbf{else}\ S_2 \mid \mathbf{while}\,(B)\,S_1 \mid \{\,L\,\} \mid A\,;\\
L &\to L_1\,S \mid S
\end{align*}

\toprule

\begin{notebox}{Why the markers?}
$M$ \emph{remembers a position}: ``this is where the code for $S_1$ (or for the test) begins''. $N$ \emph{generates the jump over the else-part} and returns it for later patching. In the \textbf{while} rule the loop-back jump uses $M_1$, which was recorded \emph{before} $B.code$ was generated.
\end{notebox}

\begin{examplebox}{Worked example: \texttt{while (a < b) \{ if (c < d) x = y + z; \}}}
Assume numbering starts at 100; $M_1.instr=100$.

\item $M_2.instr = 102$.
\item Inner $B' \equiv c<d$: \texttt{102: if c<d goto \_}, \texttt{103: goto \_}; $\ B'.truelist=\{102\}$, $B'.falselist=\{103\}$.

\item \textbf{while}: $\mathit{backpatch}(\{103\},100)$ (i.e., \texttt{103: goto 100}); $\ \mathit{backpatch}(\{100\},102)$ (i.e., \texttt{100: if a<b goto 102}); $\ S.nextlist=B.falselist=\{101\}$; emit \texttt{106: goto 100}.
\end{enumerate}

104:  t1 = y + z

\section{Switch Statements and Procedure Calls (Brief)}

\subsection{Switch statement}
\label{sec:switch}
\begin{lstlisting}
switch (E) {
    case V1: S1
    case V2: S2
    ...
    case V(n-1): S(n-1)
    default: Sn
}
\end{lstlisting}
\textbf{Translation scheme:} evaluate $E$ into a temporary $t$, then a sequence of tests, followed by the code of each case.
\begin{lstlisting}
        code to evaluate E into t
        goto test
L1:     code for S1
        goto next
L2:     code for S2
        goto next
 ...
Ln:     code for Sn
        goto next
test:   if t = V1 goto L1
        if t = V2 goto L2
        ...
        if t = V(n-1) goto L(n-1)
        goto Ln
next:
\end{lstlisting}
Putting the tests \emph{after} the case bodies lets the code generator recognise the test sequence and implement it with a \textbf{jump table} (for dense values) or binary search. The \texttt{case} instruction can also be used: \texttt{case t V1 L1}\; \dots\; \texttt{case t V(n-1) L(n-1)}; \texttt{case t t Ln} (the last entry is the default).

\begin{notebox}{Break and fall-through}
The scheme above puts \texttt{goto next} after every case body, which is the behaviour of Pascal-like \texttt{case} statements. In C and Java a body \emph{falls through} into the next one unless it ends with \texttt{break}; to translate those, emit \texttt{goto next} only for \texttt{break}, and leave it out otherwise.
\end{notebox}

\begin{examplebox}{Worked example}
\begin{lstlisting}
switch (c) {
    case 1:  x = 10; break;
    case 2:  x = 20; break;
    default: x = 0;
}
\end{lstlisting}
(The selector is a variable, so no code is needed to evaluate it and $t=c$.)
\begin{lstlisting}
        goto test
L1:     x = 10
        goto next
L2:     x = 20
        goto next
L3:     x = 0
        goto next
test:   if c = 1 goto L1
        if c = 2 goto L2
        goto L3
next:
\end{lstlisting}
Because the tests are collected at the end, the code generator can see that the values $1,2,\dots$ are dense and replace them by one indexed jump through a table $[L_1,L_2]$ after the range check $1\le c\le2$.
\end{examplebox}

\subsection{Procedure calls}
For a call $\mathit{id}(E_1, E_2, \dots, E_n)$:
\begin{lstlisting}
        code to evaluate E1 into t1
        code to evaluate E2 into t2
        ...
        code to evaluate En into tn
        param t1
        param t2
        ...
        param tn
        call id, n          // or:  y = call id, n   if a value is returned
\end{lstlisting}
Grammar and actions (the parameter addresses are collected in a queue, and then emitted as \texttt{param}):
\begin{align*}
S &\to \mathbf{call}\ \mathbf{id}\,(\,\mathit{Elist}\,) &&\{\ \text{for each } t \text{ in queue: } \mathit{gen}(\tok{param}\ t);\ \mathit{gen}(\tok{call}\ \at{\mathbf{id}}{addr},\ \mathit{size}(\mathit{queue}));\ \}\\
\mathit{Elist} &\to \mathit{Elist}\,,\,E &&\{\ \text{append } \at{E}{addr} \text{ to the end of } \mathit{queue};\ \}\\
\mathit{Elist} &\to E &&\{\ \mathit{queue}=[\,\at{E}{addr}\,];\ \}
\end{align*}

\begin{examplebox}{Worked example: $y = f(a+b,\ c*2)$}
The arguments are evaluated first, left to right, then the \texttt{param} instructions are emitted, and finally the call:
\begin{lstlisting}
t1 = a + b
t2 = c * 2
param t1
param t2
y = call f, 2
\end{lstlisting}
\end{examplebox}

\begin{pitfallbox}{One global queue is not enough for nested calls}
Take $f(a,\ g(b))$. After the first argument the queue of $f$ is $[a]$. Parsing $g(b)$ then runs $\mathit{Elist}\to E$, which \emph{resets} the same queue to $[b]$, destroying $f$'s pending $a$. The fix is to keep the list as a synthesized attribute (\at{Elist}{list}), or equivalently to use a \emph{stack} of queues. The correct code is
\begin{lstlisting}
param b
t1 = call g, 1
param a
param t1
t2 = call f, 2
\end{lstlisting}
\end{pitfallbox}

\begin{examplebox}{Translating a small program fragment to three-address code}
Source fragment (all variables are \texttt{int}; \texttt{a} is \texttt{int a[10]}, so $w=4$):
\begin{lstlisting}
i = 0;
while (i < n && a[i] != key)
    i = i + 1;
\end{lstlisting}

\textbf{Using the label-based SDD.} $P \to S$ gives \at{S}{next} $=L_0$. For the sequence $S_1\,S_2$ (the assignment, then the loop) a label $L_1 = \at{S_1}{next}$ is placed between them. For the loop, $\mathit{begin}=L_2$, \at{B}{true} $=L_3$, \at{B}{false} $=L_0$, and the body's \at{S_1}{next} $= L_2$. For $B = B_1 \,\&\&\, B_2$ a new label $L_4 = B_1.\mathit{true}$ is created, with $B_1.\mathit{false}=L_0$, $B_2.\mathit{true}=L_3$, $B_2.\mathit{false}=L_0$.

\begin{lstlisting}
        i = 0
L1:
L2:     if i < n goto L4     // B1 (begin of while)
        goto L0              // B1 false -> exit loop
L4:     t1 = i * 4           // B2: a[i] != key
        t2 = a[t1]
        if t2 != key goto L3
        goto L0              // B false -> exit loop
L3:     t3 = i + 1           // loop body
        i = t3
        goto L2              // back to begin
L0:
\end{lstlisting}
(\texttt{L1} and \texttt{L2} label the same instruction; a later pass can merge them.)

\textbf{Using backpatching} (instruction numbering from 100). Here $M_1.\mathit{instr}=101$ (start of loop), the marker of $\&\&$ gives $103$, and $M_2.\mathit{instr}=107$ (start of body).
\begin{lstlisting}
100:  i = 0
101:  if i < n goto 103         // patched by the && marker
102:  goto _                    // on B.falselist = S.nextlist
103:  t1 = i * 4
104:  t2 = a[t1]
105:  if t2 != key goto 107     // truelist patched with M2 = 107
106:  goto _                    // on B.falselist = S.nextlist
107:  t3 = i + 1
108:  i = t3
109:  goto 101                  // emitted by the while rule (M1)
110:  ...                       // {102, 106} are backpatched with 110
\end{lstlisting}
Both of the incomplete jumps at 102 and 106 form \at{S}{nextlist} of the loop; whoever follows the loop will patch them with the index of the next instruction, here 110.
\end{examplebox}

\section{Summary and Key Takeaways}
%====================================================================

\begin{itemize}
\item Intermediate code (syntax trees, DAGs, three-address code in quadruple/triple form) decouples front and back ends and enables machine-independent optimisation.
\item A CFG gives syntax (is it a legal program, what is its structure) but not meaning. An \textbf{SDD} attaches \emph{attributes} to grammar symbols and \emph{semantic rules} to productions; \textbf{synthesized} attributes flow upward, \textbf{inherited} attributes flow downward or sideways. \textbf{S-attributed} $\subset$ \textbf{L-attributed}.
\item An \textbf{SDT} embeds the actions in the grammar and fixes the order of evaluation. S-attributed SDDs $\to$ \emph{postfix SDTs} (bottom-up). L-attributed SDDs can be implemented during top-down parsing, or, for LR grammars and with marker nonterminals, during bottom-up parsing.
\item Expressions: \at{E}{addr} holds the result; \textit{gen} emits TAC; temporaries are created by \textit{newTemp}. Array references use offsets computed from the widths of sub-arrays.
\item Boolean expressions are translated into \textbf{jumping code}, using the inherited labels \textit{true/false}. Statements use \textit{next}.
\item \textbf{Removing left recursion} (needed for top-down parsing) works for an SDD and for an SDT alike: rewrite the grammar as $A\to X\,R$, $R\to Y\,R\mid\varepsilon$; initialise the inherited $R.i$ in the base case, update it in each repeated group, copy $R.i$ to the synthesized $R.s$ at $\varepsilon$, and copy $R.s$ to the head. For an SDD write these as equations (the result is L-attributed); for an SDT place them as actions, inherited ones just before their symbol and synthesized ones of the head at the end.
\item An L-attributed SDT can be executed during \textbf{top-down parsing} in three ways: (A) recursive descent in which the inherited attributes are arguments and the synthesized attributes are return values; (B) on-the-fly generation, where the pieces of the code attribute are printed instead of being concatenated (possible when they appear in the same order as in the body); (C) a table-driven LL parser that keeps the attributes in action records and synthesize records on its stack.
\item \textbf{Backpatching} replaces inherited labels by synthesized lists (\textit{makelist, merge, backpatch}), allowing one-pass bottom-up generation with markers $M$ and $N$.
\end{itemize}

\begin{pitfallbox}{Common mistakes (check your own answers against these)}
\begin{itemize}[nosep]
\item Reading a \emph{value number} as the value of the expression. It is only the index of a record.
\item Forgetting that a DAG shares a node only if \emph{operator and both children} match; $b+a$ and $a+b$ are different unless the operands are put in canonical order.
\item Using $B.true$ where $S.next$ is meant: $S.next$ is where control goes \emph{after} a statement, $B.true$ is where it goes \emph{into} the body.
\item In a postfix SDT, putting an action in the middle of a body and expecting an LR parser to run it there; use a marker.
\item Off-by-one errors in backpatching: $M.instr$ is the index of the \emph{next} instruction to be emitted, not of the last one.
\item Treating array subscripts as indices in the three-address code; they are scaled to byte offsets.
\item Evaluating both operands of $\&\&$ / $||$ in jumping code, which loses short-circuit behaviour.
\end{itemize}
\end{pitfallbox}

\end{lstlisting}

\textbf{Q15.} Triples: $0:(+,a,b)$, $1:(*,c,d)$, $2:(-,(0),(1))$, $3:(=,x,(2))$. \textbf{Q17.} Creation order: $p_1$ = leaf $a$; $p_2$ = leaf $b$; $p_3$ = leaf $3$; $p_4=\mathit{Node}(\tok{'+'},p_2,p_3)$; $p_5=\mathit{Node}(\tok{'-'},p_1,p_4)$; $p_6$ = leaf $c$; $p_7=\mathit{Node}(\tok{'-'},p_5,p_6)$. The rules $E\to T$ and $T\to(E)$ create nothing. The root $p_7$ has the children $p_5$ (the node $a-(b+3)$) and $p_6$ ($c$); seven nodes for four operands ($2\cdot4-1=7$).

\textbf{Q18.} The prints occur in the order \texttt{a, b, +, c, *, d, e, /, -}, so the output is \texttt{ab+c*de/-}. The right-recursive scheme prints the same string, because its actions stand right after the operand they follow.

\textbf{Q19.} Grammar: $B\to D\,R$, \ $R\to D\,R\mid\varepsilon$, \ $D\to\mathbf{0}\mid\mathbf{1}$.\\
(a) SDD: $B\to D\,R$: $\at{R}{i}=\at{D}{val}$, $\at{B}{val}=\at{R}{s}$; \ $R\to D\,R_1$: $\at{R_1}{i}=2\cdot\at{R}{i}+\at{D}{val}$, $\at{R}{s}=\at{R_1}{s}$; \ $R\to\varepsilon$: $\at{R}{s}=\at{R}{i}$; \ $D$ unchanged.\\
(b) SDT:
\begin{align*}
B &\to D\ \{\ \at{R}{i}=\at{D}{val}\ \}\ R\ \{\ \at{B}{val}=\at{R}{s}\ \}\\
R &\to D\ \{\ \at{R_1}{i}=2\cdot\at{R}{i}+\at{D}{val}\ \}\ R_1\ \{\ \at{R}{s}=\at{R_1}{s}\ \}\ \mid\ \varepsilon\ \{\ \at{R}{s}=\at{R}{i}\ \}
\end{align*}
For \texttt{101}: $R.i=1$; after the digit 0 the next $R$ gets $2\cdot1+0=2$; after the digit 1 it gets $2\cdot2+1=5$; $R\to\varepsilon$ gives $R.s=5$, so $B.val=5$.

\textbf{Q20.} $B.t=\mathit{float}$ is copied down as $C.b=\mathit{float}$ through three levels; the empty production gives $C.t=\mathit{float}$, and on the way up $C.t$ becomes $\mathit{array}(6,\mathit{float})$, then $\mathit{array}(5,\mathit{array}(6,\mathit{float}))$, and finally $T.t=\mathit{array}(4,\mathit{array}(5,\mathit{array}(6,\mathit{float})))$. The procedure is the one of Example~A1: if the next token is \texttt{[}, read the number $n$, call \texttt{C(b)} recursively and return \texttt{array(n, c1)}; otherwise return \texttt{b}.

\textbf{Q22.} SDT:
\begin{align*}
S \to \mathbf{if}\ \tok{(}\ &\{\ L_1=\mathit{new}();\ \at{C}{true}=L_1;\ \at{C}{false}=\at{S}{next}\ \}\ C\ \tok{)}\\
&\{\ \mathit{print}(\text{``label''},L_1);\ \at{S_1}{next}=\at{S}{next}\ \}\ S_1
\end{align*}
\begin{lstlisting}
void S(label next) {
    label L1;
    if (look == IF) {
        match(IF);  match('(');
        L1 = new();
        C(next, L1);               // C.false = S.next, C.true = L1 ; C prints its code
        match(')');
        print("label", L1);
        S(next);                   // S1.next = S.next ; S1 prints its code
    }
    else { /* other statement types */ }
}
\end{lstlisting}
On-the-fly generation is possible because $S.code$ is the concatenation of $C.code$, the label, and $S_1.code$, in the same order as $C$, $S_1$ appear in the body. Printing each piece when it becomes available gives the right order.
