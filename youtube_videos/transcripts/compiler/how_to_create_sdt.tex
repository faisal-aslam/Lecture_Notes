\section{Introduction}

We are given the following context-free grammar (CFG):
\[
\begin{aligned}
E &\to T\,R \\
R &\to +\,T\,R \mid -\,T\,R \mid \epsilon \mid \text{num}
\end{aligned}
\]

\textbf{Note:} The production \(R \to \text{num}\) appears to be problematic for the intended grammar. 
A more standard left-recursive or right-recursive grammar for addition and subtraction is:
\[
\begin{aligned}
E &\to E + T \mid E - T \mid T \\
T &\to \text{num}
\end{aligned}
\]
However, to stay close to the given grammar, we interpret it as a right-recursive grammar where 
\(T\) is a nonterminal that derives a number, and the \(R \to \text{num}\) production is likely a typo. 
For the purpose of this SDT, we will use the following corrected grammar (still right-recursive):
\[
\begin{aligned}
E &\to T\,R \\
R &\to +\,T\,R \mid -\,T\,R \mid \epsilon \\
T &\to \text{num}
\end{aligned}
\]
This grammar correctly generates expressions like \texttt{3+7-5} and is suitable for an SDT that computes the value and counts operations.

The goal is to create a calculator that:
\begin{itemize}
  \item Computes the final result of an expression with addition and subtraction.
  \item Counts the total number of operations (additions and subtractions) performed.
  \item Prints the result and the operation count using simple C \texttt{printf} statements.
\end{itemize}

\section{Derivation and Parse Tree}

Consider the input expression \texttt{3+7-5}. 
Using the corrected grammar:
\[
\begin{aligned}
E &\to T\,R \\
T &\to \text{num} \\
R &\to +\,T\,R \mid -\,T\,R \mid \epsilon
\end{aligned}
\]
A leftmost derivation is:
\[
E \Rightarrow T\,R \Rightarrow \text{num}\,R 
\Rightarrow \text{num} + T\,R 
\Rightarrow \text{num} + \text{num}\,R 
\Rightarrow \text{num} + \text{num} - T\,R 
\Rightarrow \text{num} + \text{num} - \text{num}\,R 
\Rightarrow \text{num} + \text{num} - \text{num}
\]
where the last step uses \(R \to \epsilon\).

The corresponding parse tree is shown below.

\section{Syntax-Directed Translation (SDT)}

We use synthesized attributes to compute the value and operation count. 
Each nonterminal \(E\), \(T\), and \(R\) will have two attributes:
\begin{itemize}
  \item \texttt{val}: the numerical value of the subexpression.
  \item \texttt{cnt}: the number of operations performed in the subexpression.
\end{itemize}

\subsection{Semantic Rules}

The SDT rules are given below. 
We use a simple C-like notation for the actions.

\begin{center}
\begin{tabular}{ll}
\toprule
\textbf{Production} & \textbf{Semantic Rules} \\
\midrule
\(E \to T\,R\) 
& \(E.\text{val} = T.\text{val} + R.\text{val}\) \\
& \(E.\text{cnt} = R.\text{cnt}\) \\
\midrule
\(R \to +\,T\,R_1\) 
& \(R.\text{val} = T.\text{val} + R_1.\text{val}\) \\
& \(R.\text{cnt} = R_1.\text{cnt} + 1\) \\
\midrule
\(R \to -\,T\,R_1\) 
& \(R.\text{val} = T.\text{val} - R_1.\text{val}\) \\
& \(R.\text{cnt} = R_1.\text{cnt} + 1\) \\
\midrule
\(R \to \epsilon\) 
& \(R.\text{val} = 0\) \\
& \(R.\text{cnt} = 0\) \\
\midrule
\(T \to \text{num}\) 
& \(T.\text{val} = \text{num.value}\) \\
& \(T.\text{cnt} = 0\) \\
\bottomrule
\end{tabular}
\end{center}

\subsection{Explanation}

\begin{itemize}
  \item For \(E \to T\,R\), the value of \(E\) is the value of \(T\) plus the value of \(R\). 
        The operation count is simply the count from \(R\) (since \(T\) contributes no operations).
  \item For \(R \to +\,T\,R_1\), the value is \(T.\text{val} + R_1.\text{val}\). 
        The operation count is \(R_1.\text{cnt} + 1\) because we perform one addition.
  \item For \(R \to -\,T\,R_1\), the value is \(T.\text{val} - R_1.\text{val}\). 
        The operation count is \(R_1.\text{cnt} + 1\) because we perform one subtraction.
  \item For \(R \to \epsilon\), the value is \(0\) and the count is \(0\) (base case for the right-recursive list).
  \item For \(T \to \text{num}\), the value is the number's value and the count is \(0\).
\end{itemize}

\subsection{Example: \texttt{3+7-5}}

Using the SDT rules, we can evaluate the expression:
\begin{itemize}
  \item \(T_1 \to \text{num}(3)\): \(T_1.\text{val} = 3\), \(T_1.\text{cnt} = 0\).
  \item \(T_2 \to \text{num}(7)\): \(T_2.\text{val} = 7\), \(T_2.\text{cnt} = 0\).
  \item \(T_3 \to \text{num}(5)\): \(T_3.\text{val} = 5\), \(T_3.\text{cnt} = 0\).
  \item \(R_3 \to \epsilon\): \(R_3.\text{val} = 0\), \(R_3.\text{cnt} = 0\).
  \item \(R_2 \to -\,T_3\,R_3\): 
        \(R_2.\text{val} = 5 - 0 = 5\), 
        \(R_2.\text{cnt} = 0 + 1 = 1\).
  \item \(R_1 \to +\,T_2\,R_2\): 
        \(R_1.\text{val} = 7 + 5 = 12\), 
        \(R_1.\text{cnt} = 1 + 1 = 2\).
  \item \(E \to T_1\,R_1\): 
        \(E.\text{val} = 3 + 12 = 15\), 
        \(E.\text{cnt} = 2\).
\end{itemize}

The final result is \(15\), and the number of operations is \(2\). 
(Note: The example in the problem statement says \texttt{3+7-5} yields \texttt{total=5}, which seems incorrect; 
\(3+7-5 = 5\) is the value, but the example says \texttt{total=5} and operations=2. 
Actually, \(3+7-5 = 5\), so the value is 5. The operation count is 2. 
The problem statement's example ``total=5'' likely means the final value is 5. 
Our SDT computes the value correctly as 15? Wait, \(3+7-5 = 5\), not 15. 
Let's re-evaluate: \(3 + 7 - 5 = 10 - 5 = 5\). 
Our calculation above gave \(R_2.\text{val} = 5 - 0 = 5\) (but that's for the subexpression ``-5''), 
then \(R_1.\text{val} = 7 + 5 = 12\)? That is wrong because the subtraction should apply to the whole previous result, 
not just to the 5. The grammar \(R \to +\,T\,R \mid -\,T\,R\) with right recursion evaluates as 
\(3 + (7 - 5) = 3 + 2 = 5\), which is correct. 
Let's recompute:
\(R_3 \to \epsilon\): val=0, cnt=0.
\(R_2 \to -\,T_3\,R_3\): val = \(5 - 0 = 5\)? No, the rule is \(R.\text{val} = T.\text{val} - R_1.\text{val}\). 
So \(R_2.\text{val} = T_3.\text{val} - R_3.\text{val} = 5 - 0 = 5\). 
But this means the subexpression ``-5'' evaluates to 5, which is wrong. 
The problem is that the subtraction should be \(T.\text{val} - R_1.\text{val}\)? 
Actually, for right recursion, the expression is \(T_1 + T_2 - T_3\), which parses as \(T_1 + (T_2 - T_3)\). 
So \(R_1\) should represent ``+ T_2 - T_3'', and its value should be \(T_2 - T_3\). 
Thus for \(R \to -\,T\,R_1\), the value should be \(T.\text{val} - R_1.\text{val}\)? 
Wait, if \(R_1\) represents the rest after the minus sign, then the expression is \(T - R_1\). 
But in the parse tree, \(R \to -\,T\,R_1\) means the minus sign comes first, then \(T\), then \(R_1\). 
So the expression is \(-T + R_1\)? That's not right. 
The grammar is ambiguous or incorrectly written for standard arithmetic. 
The standard right-recursive grammar for addition and subtraction is:
\(E \to T\,R\)
\(R \to +\,T\,R \mid -\,T\,R \mid \epsilon\)
But this grammar generates strings like ``+ 3 - 5'' which is not standard infix. 
Actually, the grammar \(E \to T\,R\), \(R \to +\,T\,R \mid -\,T\,R \mid \epsilon\) generates 
\(T (+ T)^* (- T)^*\)? No, it generates \(T (+ T | - T)^*\) but the operators are prefix? 
Wait, the production \(R \to +\,T\,R\) means the plus sign comes before \(T\) and \(R\). 
So the string is \(T + T + T ...\) which is infix if we consider the plus sign as a separator? 
No, the string is \(T + T R\), so the plus sign is between \(T\) and \(T\). 
Actually, \(E \to T R\) and \(R \to + T R\) gives \(T + T R\), so the plus is between the first \(T\) and the second \(T\). 
So the string is \(T + T + T ...\) which is infix. 
But the parse tree for \(3+7-5\) would be:
\(E \to T R\)
\(T \to 3\)
\(R \to + T R\) (with \(T \to 7\))
\(R \to - T R\) (with \(T \to 5\))
\(R \to \epsilon\)
This gives the string \(3 + 7 - 5\). 
The evaluation should be: \(R\) after \(+7\) is \(-5\), which evaluates to \(-5\)? 
No, the \(R\) after \(+7\) represents the rest of the expression after \(7\), which is \(-5\). 
So \(R_1\) (after \(+7\)) has value \(-5\)? 
Then \(R_1.\text{val}\) should be \(-5\), and \(E.\text{val} = 3 + (-5) = -2\), which is wrong. 
The issue is that the minus sign is part of the \(R\) production, so the value of \(R \to - T R_1\) should be 
\(-T.\text{val} + R_1.\text{val}\)? 
Let's think: the string generated by \(R \to - T R_1\) is ``- T R_1''. 
If we interpret this as a suffix to be added to the previous value, then the minus sign applies to \(T\), 
so the contribution is \(-T.\text{val} + R_1.\text{val}\). 
But that would make \(3 + 7 - 5\) evaluate as \(3 + (7) + (-5) = 5\), which is correct. 
So the semantic rule for \(R \to - T R_1\) should be:
\(R.\text{val} = -T.\text{val} + R_1.\text{val}\).
Similarly, for \(R \to + T R_1\):
\(R.\text{val} = T.\text{val} + R_1.\text{val}\).
Then for \(E \to T R\):
\(E.\text{val} = T.\text{val} + R.\text{val}\).
Let's test with \(3+7-5\):
\(T_1=3\), \(T_2=7\), \(T_3=5\).
\(R_3 \to \epsilon\): val=0, cnt=0.
\(R_2 \to - T_3 R_3\): val = \(-5 + 0 = -5\), cnt = 0+1=1.
\(R_1 \to + T_2 R_2\): val = \(7 + (-5) = 2\), cnt = 1+1=2.
\(E \to T_1 R_1\): val = \(3 + 2 = 5\), cnt = 2.
Correct! The value is 5, operations=2. 
So the corrected semantic rules are:
\begin{itemize}
  \item \(E \to T R\): \(E.\text{val} = T.\text{val} + R.\text{val}\), \(E.\text{cnt} = R.\text{cnt}\)
  \item \(R \to + T R_1\): \(R.\text{val} = T.\text{val} + R_1.\text{val}\), \(R.\text{cnt} = R_1.\text{cnt} + 1\)
  \item \(R \to - T R_1\): \(R.\text{val} = -T.\text{val} + R_1.\text{val}\), \(R.\text{cnt} = R_1.\text{cnt} + 1\)
  \item \(R \to \epsilon\): \(R.\text{val} = 0\), \(R.\text{cnt} = 0\)
  \item \(T \to \text{num}\): \(T.\text{val} = \text{num.value}\), \(T.\text{cnt} = 0\)
\end{itemize}
This matches the example: \(3+7-5\) gives value 5 and operations 2.

\section{C Code for the SDT}

Below is a simple C implementation of the SDT using a recursive descent parser. 
It computes the value and operation count and prints them.

\begin{lstlisting}
#include <stdio.h>
#include <stdlib.h>
#include <ctype.h>

// Global variable to hold the current input character
char *input;
int pos = 0;

// Function prototypes
int E(int *cnt);
int T(int *cnt);
int R(int *cnt);
int num(int *cnt);

// Parse E -> T R
int E(int *cnt) {
    int val = T(cnt);
    val += R(cnt);
    return val;
}

// Parse R -> + T R | - T R | epsilon
int R(int *cnt) {
    if (input[pos] == '+') {
        pos++; // consume '+'
        int t = T(cnt);
        int r = R(cnt);
        (*cnt)++; // one addition
        return t + r;
    } else if (input[pos] == '-') {
        pos++; // consume '-'
        int t = T(cnt);
        int r = R(cnt);
        (*cnt)++; // one subtraction
        return -t + r;
    } else {
        // epsilon
        return 0;
    }
}

// Parse T -> num
int T(int *cnt) {
    return num(cnt);
}

// Parse a number
int num(int *cnt) {
    int val = 0;
    while (isdigit(input[pos])) {
        val = val * 10 + (input[pos] - '0');
        pos++;
    }
    return val;
}

int main() {
    char expr[100];
    printf("Enter expression: ");
    scanf("%s", expr);
    input = expr;
    pos = 0;
    int cnt = 0;
    int result = E(&cnt);
    printf("total=%d and the number of operations=%d\n", result, cnt);
    return 0;
}
\end{lstlisting}

\section{Conclusion}

We have constructed an SDT for a calculator grammar that handles addition and subtraction, 
computes the final result, and counts the number of operations. 
The semantic rules use synthesized attributes \texttt{val} and \texttt{cnt}. 
The provided C code implements the SDT using recursive descent and prints the result 
and operation count as required. 
The corrected grammar and semantic rules ensure that expressions like \texttt{3+7-5} 
are evaluated correctly as \(3 + (7 - 5) = 5\) with 2 operations.
